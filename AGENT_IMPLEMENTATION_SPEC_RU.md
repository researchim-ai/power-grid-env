# Техническое задание агенту: платформа инженерной проверки алгоритмов энергосетей

Редакция 0.2 · 25 октября 2026. Требования и целевые критерии, не описание уже реализованных возможностей. Основной документ для исполнения; при расхождении приоритет имеет он, затем архитектурный план.

## 1. Правило исполнения

Реализовать открытую платформу инженерной проверки алгоритмов управления электроэнергетическими сетями на высокодостоверной физической модели. Основной workflow: загрузить модель сети → подключить внешний алгоритм → задать испытания → сравнить с baseline → получить воспроизводимый отчёт и разобрать причины нарушений. Обучение RL/ML/LLM/VLM и генерация датасетов используют то же ядро и являются самостоятельными возможностями платформы.

Идти по зависимостям ниже без календарных обязательств. Для каждого этапа подготовить работающий код, документацию уравнений и допущений, тестовые кейсы, отчёт о численной проверке и воспроизводимую команду запуска. Не подменять реализацию заглушками, заранее записанными ответами и тестами, повторяющими код.

Высокая точность — совокупность адекватности физической модели, достоверности параметров, численной погрешности и корректности событий. Малый residual не подтверждает реалистичность оборудования. Согласие двух библиотек не подтверждает истинность общей аппроксимации. Синтетический benchmark не подтверждает работу на реальном объекте.

Функция получает статус validated только для перечисленных семейств моделей и режимов. Статусы: planned, implemented, numerically_verified, cross_validated, validated_for_declared_scope. При отсутствии натурных данных явно указывать предел доказательств. Область применимости расширять отдельными проверками.

### 1.1. Первый законченный продукт

Пользователь первого релиза — разработчик алгоритма восстановления распределительной сети: автоматики, ADMS/DERMS или исследовательского контроллера. Входы: модель фидера, доступные измерения, правила эксплуатации, сценарии и исполняемый алгоритм. Выход: сравнение с baseline, нарушения с привязкой к времени и оборудованию, метрики восстановления, диагностика и replay.

Первая область приёмки: квазистационарная несимметричная сеть, известный повреждённый участок, отключения и допустимые переключения. Несимметрия, ограничения напряжения/тока, обесточенные секции и критические нагрузки обязательны. Поддерживаемые соединения трансформаторов, модели нагрузок и заземления перечислить в capability manifest. Если cold-load pickup влияет на испытание, включить проверенную модель либо явно ограничить выводы; неизвестные параметры не выдумывать.

Это законченный инструмент испытаний, полезный без реализации всей библиотеки RMS/EMT. Проверка DER-управления — следующий самостоятельный task pack. Магистральные сети, RMS, EMT и детальная релейная защита остаются целевыми расширениями с отдельной приёмкой, а не обязательными условиями выпуска первой версии.

### 1.2. Использование решателей

В первом продукте интегрировать проверенный внешний phase-domain backend через собственный контракт. Свой solver писать только при зафиксированном пробеле существующих backend и наличии независимых эталонов. Использование внешнего решателя не снижает требования к физике: проверить отображение оборудования, параметры, события, ограничения и результаты на поддерживаемой области. Собственный код решателя сам по себе не является критерием ценности.

### 1.3. Критерий продуктовой готовности

На отдельной модели и внешнем контроллере, которые не зашиты в код demo, пользователь самостоятельно выполняет полный цикл import → preflight → suite → compare → report → replay. Данные и алгоритм меняются через публичные интерфейсы. Отчёт показывает случаи, где алгоритм хуже baseline, и все неоценённые случаи. Отсутствие подтверждённых коммерческих заказов не блокирует техническую реализацию; готовность продукта не объявлять доказательством спроса.

## 2. Физические контракты до кода решателя

Сначала реализовать документ и машинные схемы конвенций:

- Направления P/Q/I, генераторная и потребительская конвенции; ориентация ветвей; порядок фаз и направление углов.
- SI и отображаемые единицы; bases для per-unit, переход через трансформатор; line-to-line против line-to-neutral; peak против RMS.
- Phasor frequency, комплексные сопряжения, углы в rad во внутреннем API; degrees только с явной конвертацией.
- Ground reference, нейтраль, positive/negative/zero sequence; применимость симметричных составляющих.
- Раздельные topology model, equipment parameters, physical state, estimated state и measured observation.
- Terminal/connectivity-node модель для подстанций и вывод bus-branch расчётной модели. Постоянные идентификаторы при пересборке шин.
- Параметры с источником, timestamp, quality и uncertainty. Нет молчаливого заполнения неизвестной схемы соединения или заземления.

До дальнейшей разработки принять аналитические тесты преобразования единиц, знаков, фаз, баз и комплексной мощности S = V·conj(I). Ошибки таких конвенций должны выявляться на минимальных схемах.

## 3. Стационарные режимы передачи

Собственное контролируемое интерфейсом расчётное ядро должно поддерживать AC power flow; первое время допустим проверенный внешний backend. Для собственного решателя: sparse Newton–Raphson, аналитический Jacobian, контроль масштабирования и residual, damping/line search по необходимости. Alternative formulation и continuation — отдельные последующие улучшения, когда есть сложные кейсы.

Модели: PI-линии с charging и shunts; двух- и трёхобмоточные трансформаторы с отношением, фазовым сдвигом и выбранным представлением потерь; PQ/PV/slack, distributed slack с заданной политикой; ZIP-нагрузки; реактивные пределы и корректный переход PV↔PQ; РПН, шунтирующие ступени и внешние циклы регулирования с гистерезисом и пределами итераций.

Каждый электрический остров имеет явную политику баланса. Остров без источника не получает искусственное питание; несколько grid-forming источников требуют определённого распределения. Сингулярность и отсутствие физически допустимого режима не смешивать. Статус несходимости должен сохранять диагностику и последнюю итерацию как диагностические данные.

DC power flow, PTDF/LODF и sensitivities реализовать как приближения с указанной точкой линеаризации. Проверять sensitivities конечными разностями вдали от смены активного набора; обнаруживать потерю применимости при островообразовании и изменении топологии.

## 4. Несимметричные распределительные сети

Реализовать phase-domain модель ABC с отсутствующими фазами, одно-/двух-/трёхфазными нагрузками, взаимными импедансами и shunt admittance. Четырёхпроводные сети моделировать с явной нейтралью в соответствующем режиме. Kron reduction разрешать только при выполнении задокументированных предпосылок; он не универсальная замена нейтрали.

Трансформаторы: wye/delta, vector group, фазовые сдвиги, нейтраль и заземление, регулирование, поддерживаемые варианты трёхобмоточных соединений. Проверять propagation zero sequence и невозможность переноса её через неподходящее соединение. Матрицы элементов и преобразование выводов должны иметь отдельные reference tests.

Loads: phase-specific P/Q, ZIP и временные профили. Добавить cold-load pickup и зависимость от времени после восстановления как отдельную параметризованную модель. Motors и frequency sensitivity не имитировать статическим ZIP без явного обозначения.

DER: PV и накопители с ограничением apparent power, P/Q priority, Volt-VAR/Volt-Watt, ramp limits, реакцией на напряжение и доступностью. Battery SoC обновлять по фактически исполненной мощности, продолжительности и эффективности; не допускать создания энергии при clipping.

Расчёт: проверенный phase-domain backend первым; затем собственный метод только при конкретной потребности. Для radial и weakly meshed кейсов сравнивать применимые методы на общей модели. Нельзя считать совпадение с positive-sequence solver проверкой несимметрии.

## 5. Квазистационарное время и коммутация

Событийная модель со стабильным порядком и явным временем. Различать решение агента, принятие команды, физическое исполнение и поступление телеметрии. Временной шаг управления не равен временному шагу физики.

Состояние контроллеров включает таймеры, deadbands, integrators при наличии, hysteresis, lockout и очереди команд. Переключения имеют предусловия, допустимую коммутационную способность и задержку. Разъединитель не равен выключателю. Учитывать запрет подачи напряжения на ремонтируемый участок и запрет несинхронного соединения островов в режимах, где оно моделируется.

Для восстановления: известный повреждённый участок, отказ аппарата, ограничение числа операций, приоритет нагрузки, radiality policy, возможность обратного питания, cold-load pickup. Отдельно моделировать устойчивость после коммутации на подходящем динамическом backend; статическая допустимость не заменяет её.

Защиты в QSTS — явно упрощённые time-current/overload правила, полезные для соответствующего класса сценариев. Не использовать их для заявления точности быстродействующей релейной защиты.

## 6. Короткие замыкания и защиты

Самостоятельный модуль fault analysis: трёхфазные, фаза-земля, междуфазные и двухфазные на землю повреждения; fault impedance; источники и заземления; допустимые варианты sequence/phase-domain расчёта. Для инверторов отдельно задавать применимую fault-current модель: классическая эквивалентная машина не универсальна.

Разделить инженерный расчёт по выбранной методике/редакции стандарта и физический time-domain transient. Стандартный расчёт токов КЗ не заменяет воспроизведение формы тока. Конкретные стандарты и коэффициенты перед реализацией сверить с доступной авторитетной документацией и зафиксировать версию.

Защиты развивать по классам: overcurrent, directional, distance, under/over-voltage, frequency и reclosing. Для каждой указать входной сигнал, фильтр/измерительный алгоритм, pickup, time characteristic, reset и breaker delay. Проверить координацию и селективность на тестовых схемах, а не только факт отключения.

Для distance/differential и быстродействующих защит требуются адекватные измерительные и transient модели; не объявлять полный охват на основании QSTS.

## 7. RMS/phasor динамика

Отдельный DAE backend вида x_dot=f(x,y,u,t), 0=g(x,y,u,t), согласованная инициализация из power flow. Модели синхронных машин добавлять ступенчато: classical → transient → subtransient при наличии эталонов; модели AVR, governor, PSS, частотно-зависимых нагрузок и двигателей — с документированными параметрами и лимитерами.

Grid-following и grid-forming инверторы моделировать отдельно. Явно задавать bandwidth, current limits, PLL где применимо, droop/control modes и область усреднения. Средняя phasor-модель не обещает switching-waveform точность.

Численные требования: implicit integration подходящей жёсткости, sparse linear solves, управление ошибкой, consistent reinitialization после события, локализация переключений, контроль constraint drift. Первым методом допустим implicit trapezoidal с анализом его ограничений; другие схемы вводить по проверенным stiff cases.

Приёмка: equilibrium residual, small-signal consistency где применимо, известные oscillation modes, fault/clearing/line-trip сценарии; уменьшение шага и ужесточение tolerances должны давать ожидаемую сходимость траекторий. Около границы устойчивости публиковать чувствительность и диапазон неопределённости critical clearing time.

## 8. EMT как отдельная область точности

Целевой модуль: мгновенные фазные величины, RLC, трансформаторы с выбранной моделью насыщения, модели линий по частотной области применимости, коммутация и силовая электроника. Усреднённые и switching модели должны различаться в capabilities.

Не включать весь EMT в первый вертикальный срез. Сначала подготовить backend interface и обменные переменные, затем проверять аналитические RC/RL/RLC transients, energization и простой converter; только после этого расширять компонентную библиотеку.

Для RMS–EMT ко-симуляции задать границу, преобразование сигналов, coupling timestep, итерации, задержки и учёт энергии. Проверять interface stability, step sensitivity и отсутствие искусственного энерговклада. Само подключение HELICS не решает численную согласованность.

Hard real-time и hardware-in-the-loop — отдельные гарантии исполнения, а не свойство обычного быстрого offline solver.

## 9. Оптимизация, надёжность и оценка состояния

OPF: DC как линейная начальная постановка для подходящих задач; AC и unbalanced formulations — отдельно. Ограничения ветвей, напряжений, генерации, ramp, SoC и дискретных аппаратов включать явно. AC OPF не объявлять глобально оптимальным без доказательства; сохранять termination status, feasibility residual и optimality diagnostics.

MPC/dispatch: горизонт, доступный прогноз и неопределённость, ограничения конца горизонта и фактическое исполнение. Restoration MILP/MISOCP может использовать приближение сети; результат обязательно перепроверять соответствующим AC backend и корректно обрабатывать неуспех.

N−1: перечисление и идентификация contingency, корректное время аварийных лимитов, islands, remedial actions, отчёт непросчитанных случаев. Screening приближением не подменяет финальную проверку. Reliability Monte Carlo требует обоснованных failure/repair distributions и оценки статистической погрешности.

State estimation: WLS с весами измерений, observability, bad-data handling и диагностикой; затем robust/динамические варианты. Топологические ошибки, пропуски и задержки — отдельные сценарии. Нельзя отдавать агенту estimator output, скрыто использующий недоступные измерения.

## 10. Численные критерии приёмки

Начальные engineering targets ниже уточнять на conditioning и reference corpus. Агент не ослабляет пороги автоматически ради зелёного CI; изменение порога оформляет отдельным ADR с причиной и примерами.

Для хорошо обусловленных стационарных кейсов без смены дискретных режимов:

- Нормированный max power/current mismatch ≤ 1e−8 в выбранной per-unit системе, с опубликованной нормализацией и абсолютным floor для малых величин.
- Независимый расчёт на совпадающих моделях: max voltage magnitude difference ≤ 1e−5 p.u.; angle difference ≤ 1e−4 rad после согласования reference angle для каждого острова.
- Потоки и потери: mixed absolute/relative criterion. Начальный target 1e−5 p.u. абсолютной ошибки на объявленной S_base плюс 1e−4 относительной; сравнивать фазные и суммарные величины отдельно.
- Проверить KCL, complex-power balance, физически допустимые потери passive elements и boundary accounting; slack injection не должен скрывать ошибку модели нагрузки.

Для сложных regulated и near-collapse кейсов отдельно фиксировать допустимую ветвь решения и policy контроллеров. Разные положения РПН при deadband не обязательно ошибка, но требуют объяснения. Не удалять несошедшиеся случаи из сводной статистики.

Для Jacobian: аналитическая матрица против независимых finite differences/automatic differentiation там, где функция гладкая, с масштабированием и sweep размера шага. Complex-step использовать только для совместимых аналитических вычислений; conj/abs и переключения нарушают его предпосылки.

Для dynamics и EMT: case-specific mixed tolerances, шаговая сходимость, события, энергетические балансы и сопоставление ключевых физических метрик. Универсальное совпадение каждой точки в процентах для колебательной траектории не применять без учёта фазового сдвига и временного выравнивания.

Для stochastic scenarios: статистические тесты распределений, корреляций, сезонности и частоты редких событий. Фиксация seed проверяет воспроизводимость, но не реалистичность генератора.

## 11. Reference corpus

Начать с аналитических схем: одиночная нагрузка, двухузловая линия, radial three-bus, трансформатор, разрыв фазы, явная нейтраль, короткое замыкание через импеданс, один остров с источником и один без него. Затем добавить признанные публичные transmission/distribution и dynamic benchmark cases с проверкой лицензий и источника параметров.

Каждый case содержит source, license, исходные единицы, преобразования, supported scope, reference outputs, tolerances и независимый способ их получения. Не создавать эталон текущим solver и считать совпадение доказательством правильности.

Отдельные наборы: аналитическая корректность, cross-solver comparison, numerical stress, replay/event semantics, real-event validation при наличии правомерных данных. Отчёт показывает все категории и исключения, а не одну усреднённую оценку точности.

## 12. Что обязательно для AI

Держать физическое состояние закрытым от policy, выдавать причинно доступную observation. Forecast не содержит будущей истины; action mask не раскрывает скрытые аварии. Сохранять schema observations и dataset provenance.

RL: Gymnasium, partial observability, hybrid action spaces, reproducible reset, baseline/control policy, отдельный safety shield. LLM: typed tools, bounded what-if, plan preconditions и execution feedback. VLM: рендер только из observation, разнообразие схем и отдельный pixels-only UI runner. ML: временные/топологические splits, preprocessing только по train и uncertainty для surrogate.

Итог эпизода определяется физическими и эксплуатационными метриками, а не текстовой оценкой другого LLM. Публиковать нарушения исходной политики и системы с shield отдельно. Training throughput не важнее корректной физики.

## 13. Очередь реализации с gates

Первая полезная версия завершается после A–D и P ниже. Порядок чтения разделов 3–9 не определяет порядок реализации: расширенная физика E–H не блокирует первую поставку.

Этап A — specification and reference: схемы, единицы, capabilities, reference corpus, ADR и CI. Gate: аналитические эталоны и конвенции проверяются автоматически.

Этап B — первый точный steady-state slice: распределительный phase-domain backend, topology compilation, equipment subset, islands, convergence diagnostics. Gate: KCL/balance и независимые comparisons проходят объявленные допуски на всех поддержанных случаях.

Этап C — simulation engine: события, controllers, ограничения, команды, snapshots/replay. Gate: причинный порядок, отсутствие тихой порчи данных, идентичное восстановление состояния и negative tests.

Этап D — первая задача агента: restoration, эвристика, Gymnasium, recorder, LLM tools. Gate: воспроизводимый полный эпизод с отчётом о каждом нарушении; политика проверяется на отложенных сценариях.

Этап P — законченная платформа испытаний: внешний controller adapter, импорт с preflight, декларативные test suites, batch runner, независимый evaluator, compare/report/replay и минимальный инженерный просмотр. Gate: выполнены критерии разделов 16–20 на отдельном импортируемом кейсе; контроллер заменяется без изменения simulation engine. Это точка первой поставки, а не промежуточное demo.

Этап E — расширенная сеть и анализ: transmission adapter, AC/DC, sensitivities, state estimation, OPF, N−1. Принимать каждый модуль независимо; не ждать завершения всех для полезности продукта.

Этап F — RMS dynamics и protection: начинать с малого проверенного набора машин/регуляторов, добавлять события и ограничители. Gate: согласованная инициализация, шаговая сходимость и reference trajectories.

Этап G — VLM и богатые среды: инженерный UI, visual track, multi-agent и uncertainty scenarios. Базовый рендер можно начать после D; его завершение не блокирует E/F.

Этап H — EMT, ко-симуляция и ускорение: выполнять отдельными модулями после доказанного интерфейса и эталонов. Оптимизацию принимать только при неизменном качестве на numerical regression corpus.

В конце каждого этапа агент обновляет capability matrix, список открытых ограничений и команды воспроизведения. Переход к следующей физике не скрывает незавершённую валидацию предыдущей.

## 14. Обязательные артефакты репозитория

docs/physics — уравнения, конвенции, применимость и параметры каждой модели.
docs/adr — выборы решателей, моделей, импорта и порогов.
schemas — версионированные форматы модели, события, observation, action и trajectory.
cases/reference — исходные кейсы, лицензии, ожидаемые результаты и происхождение.
tests/numerical — analytical, balance, convergence, cross-backend и stress suites.
tests/scenarios — controller/event/replay/agent-information tests.
benchmarks — полные шаги среды и отдельные solver/render timings с hardware/config.
reports/validation — машинный JSON и читаемый отчёт по каждому релизу.
examples — minimal solve, restoration, RL, LLM tools и VLM.

README обязан различать implemented и validated. Публикация релиза требует numerical report. Никаких заявлений о полной промышленной точности, real-time, EMT или соответствии стандарту без соответствующего набора доказательств.

## 15. Команда запуска работ агенту

«Реализуй первую законченную версию платформы инженерной проверки по этапам A → B → C → D → P. Сначала изучи инструкции репозитория и актуальную первичную документацию выбранных зависимостей. Создай проверенное физическое ядро на внешнем phase-domain backend, независимые эталоны и полный workflow import/preflight/suite/compare/report/replay. Подключай алгоритмы через публичный изолированный интерфейс. Не начинай с масштабного UI или массового обучения; минимальный инженерный просмотр входит в P. Фиксируй уравнения, units, unsupported features и результаты проверок. Не выдавай численную несходимость за физический коллапс. После каждого gate сохраняй воспроизводимые команды и validation report. Сначала выполни приёмку первой поставки, затем продолжай E–H с отдельными критериями. Не понижай требования ради демонстрации».

## 16. Подключение внешних алгоритмов

Controller protocol не зависит от ML framework. Минимальные операции: initialize(observation_schema, action_schema, public_task_config), reset(public_episode_context), act(observation, permitted_history), close(). Ответ содержит action с единицами, correlation ID и опциональное краткое обоснование. Физические truth state и скрытая конфигурация сценария не входят в процесс контроллера.

Первый adapter — Python subprocess с версионированными структурированными сообщениями. Затем container adapter и удалённый endpoint по потребности; простой subprocess не объявлять защитной песочницей для недоверенного кода. Секреты, model files и hidden suite configuration не передавать контроллеру. Для недоверенного кода перед применением реализовать отдельную изоляцию прав, файлов и сети; ограничения внешнего LLM разрешать явно и журналировать.

Установить decision timeout, предел памяти где поддерживается runtime, квоту what-if и политику отказа. Отдельные исходы: invalid action, timeout, controller crash, backend failure, scenario invalid. При timeout фиксировать отсутствие команды и применённую политику hold/no-op; не изображать её решением алгоритма. Ограничения исполнения и доступная информация одинаковы для сравниваемых контроллеров.

Правила блокировок оборудования всегда являются частью среды. Дополнительный policy shield включается явной настройкой; режимы raw policy и policy+shield оцениваются раздельно. Блокировка команды не стирает небезопасную попытку из метрик.

Поддержать детерминированную эвристику и Gymnasium policy; LLM использует тот же execution contract через tools. Обучать собственную модель для проверки внешнего контроллера необязательно. Предусмотреть экспорт разрешённых траекторий и демонстраций для обучения.

## 17. Импорт и предварительная проверка

В первой поставке нужны канонический формат и один выбранный внешний формат. Выбрать его ADR по точности переноса первого backend; не обещать все CIM/CGMES/PSS/E форматы одновременно. Import report хранит original IDs, units, mapping, преобразования, неизвестные свойства, аппроксимации и hash источника.

Preflight проверяет целостность ссылок, units/bases, фазность, соединения и заземления, диапазоны параметров, источники в островах, initial operating point и совместимость task/solver/controller. Ошибку и предупреждение различать. Критически неизвестная характеристика не получает скрытый default; аппроксимация требует явной настройки и попадает в каждый итоговый отчёт.

Нужны отдельно физическая reference-сеть и заявленная модель, доступная алгоритму. В экспериментах model mismatch изменять их раздельно. Целевой evaluation backend остаётся фиксированным; agent what-if работает только с разрешённой моделью. Не подменять модель во время теста без события и записи provenance.

Команда preflight создаёт machine-readable validation report даже при отказе импорта; исходные файлы не изменяются. Отчёт содержит устранённые автоматически только безопасные представительные преобразования, например явную конвертацию единиц, с полным журналом.

## 18. Test suites и runner

Suite — версионированная декларация: model IDs/hashes, task, список и генератор сценариев, seeds, горизонты и timestamps, наблюдаемость, отказы, uncertainty distributions, ограничения, доступные действия, метрики, пороги приёмки и лимиты вычислений. Пороги фиксируются до итоговой оценки и не меняются по результату выбранной политики.

Первый restoration pack покрывает нормальный режим, одиночный отказ, обесточенную секцию, недоступное переключение, перегрузку при восстановлении, фазное нарушение напряжения, задержку/пропуск измерения и timeout контроллера. Каждый сценарий имеет известную цель и классификацию сложности. Правдоподобные совместные воздействия добавляются отдельно от независимого random noise.

Runner исполняет baseline и кандидат на одинаковых экзогенных сценариях, наблюдениях и лимитах доступа; endogenous события закономерно зависят от их действий. RNG источников разделены, чтобы дополнительный вызов policy не менял погоду/аварии. Сравнение парное по scenario ID; интервалы неопределённости учитывать по независимым сценариям/семействам, а не считать каждый зависимый timestep независимым наблюдением.

Поддержать cancellation, resume, идентификаторы попыток и идемпотентное сохранение. Failed runs не заменяются успешным retry молча: первоначальный исход и причина повторения остаются видимы. В отчёте отдельно отражать controller failure, simulation failure, physical violation и completed episode.

Locked evaluation отделить от training/dev. Локально доверенный разработчик может технически прочесть свой holdout; такую конфигурацию не называть защищённым закрытым тестом. Для независимой внешней оценки runner должен контролироваться стороной, не передающей скрытые файлы в controller runtime.

## 19. Независимый evaluator и комплект доказательств

Evaluator получает журнал фактического исполнения и рассчитанные состояния по отдельному read-only контракту. Он не доверяет self-reported success контроллера. Метрики определяет task pack; reward является отдельным производным сигналом. Не оценивать политики только по числу отклонённых команд: нужны последствия реально исполненных действий и качество обслуживания.

Обязательные результаты: недоотпуск энергии, доля восстановленной и критической нагрузки, время восстановления, число операций, magnitude/duration напряжения и перегрузки, нарушение блокировок, rejected actions, latency/timeout и статус полноты испытания. Если расчёт оборвался, неизвестный остаток эпизода не считать безопасным или без недоотпуска. Определение знаменателей, интеграции по времени и обращения с пропусками входит в manifest.

Для каждого существенного нарушения сохранять timestamp/interval, equipment ID, measured/calculated value, limit/unit, длительность, действие перед событием и ссылку на replay. Хронологическая связь не является доказанной причинностью: утверждать причинный эффект только после отдельного контрфактического эксперимента с описанными допущениями.

Каждый run выпускает evidence bundle: model/scenario/controller hashes, версии и конфигурации, seeds, capabilities, допущения импорта, preflight, полную трассу событий/действий/состояний, solver diagnostics, метрики, исходы и команды replay. Manifest перечисляет файлы и checksums; внешние LLM фиксируются доступным version ID и сохранёнными ответами. Recorded-response replay не обозначать повторным независимым запуском модели.

Форматы: JSON для машинных результатов, Parquet для числовых траекторий, локальный HTML для читаемого отчёта без внешних сетевых зависимостей. Отчёт содержит сравнение с baseline, распределение результатов, все сбои и исключения, область применимости и объяснение pass/fail/inconclusive. Платформа не выдаёт отраслевой сертификат или гарантию реального управления по итогам симуляции.

## 20. Приёмка первой поставки

На чистом окружении документированная последовательность команд должна:

1. Импортировать отдельный case из поддерживаемого внешнего формата; показать preflight и отклонить несовместимый case с полезной диагностикой.
2. Подключить baseline и внешний пример контроллера без изменения backend/scheduler; воспроизвести normal и timeout/crash/invalid-action исходы.
3. Выполнить restoration suite, включая случай, где кандидат нарушает ограничение или хуже baseline; сохранить эти результаты без фильтрации.
4. Выдать JSON/HTML отчёт и evidence bundle с проверяемыми checksums, явно маркированными допущениями и неоценёнными случаями.
5. Открыть минимальный инженерный просмотр: однолинейная схема, timeline, величины/пределы, предложенные и исполненные действия, переход к нарушению. Источник отображаемых величин обозначен: observation либо privileged evaluation view; второй недоступен policy.
6. Повторить детерминированную трассу в закреплённом окружении и восстановить checkpoint со всеми таймерами/очередями; численная эквивалентность соответствует объявленным допускам.
7. Подтвердить численную приёмку поддержанного equipment subset по разделам 10–11 и отсутствие утечки hidden state по разделу 12.
8. Экспортировать разрешённый dataset и запустить короткий Gymnasium rollout, подтверждая пригодность ядра для обучения. Массовое обучение и победа RL над baseline не являются условиями выпуска инструмента испытаний.

Неподдерживаемая физика перечислена в отчёте. Если для ответа на конкретный инженерный вопрос необходимы RMS/EMT или более точные параметры, исход оценки этого вопроса — out_of_scope/inconclusive. Повышать достоверность последовательным расширением области, сохраняя уже работающий workflow испытаний.
