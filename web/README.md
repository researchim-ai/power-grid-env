# power-grid-env / web

Локальный двуязычный сайт проекта: изометрическая электросеть, переключаемый
AI-слой, интерактивные иллюстрации пуска/провала/острова, графики, экспорт JSON
и документация с копированием команд. Адаптивная вёрстка, клавиатурная навигация,
режим уменьшенного движения, локальные шрифты. Внешних CDN, API и аналитики нет.

## Запуск

Из корня проекта:

```sh
cd web
npm run dev
```

Открыть `http://localhost:5173`. Node.js 20+, установка зависимостей не нужна.
Другой порт: `npm run dev -- --port 8080`. Сервер слушает только loopback.
Это локальный сервер с ограниченным API расчёта конструктора, не production backend.
Статический `dist/` показывает записи и редактор, но для запуска Python нужен этот сервер.

`index.html` можно открыть непосредственно; HTTP рекомендуется для штатной
работы буфера обмена и обновляемого JSON-снимка метрик.

## Проверка и сборка

```sh
npm run check
npm run build
```

Сборка создаёт статический `dist/`, который можно разместить на статическом
хостинге. Она обновляет локальную копию `../plans/CURRENT_STATUS.md`; историческое число
тестов B15 остаётся явно датированным снимком. Числа четырёх профилей/12 трасс и дата относятся
к опубликованному на сайте снимку B15 от 06.11.2026; при смене этого корпуса
обновите также подписи в `index.html` и переводах `app.js`.

## Структура

- `index.html` — страница, изометрические SVG-объекты и диалог документации.
- `styles.css` — дизайн, адаптивность, печать и reduced-motion.
- `app.js` — RU/EN, выбор узлов, графики и демонстрационные сценарии.
- `assets/` — локальные шрифты, лицензии, иконка и снимок статуса.
- `scripts/` — сборка и проверка без сторонних зависимостей.

## Что выполняет демонстрация

Графики старой лаборатории `index.html` — **иллюстративные**, их формулы находятся в `makeData()`.
Они не запускают Python, не являются эталонными траекториями и не предназначены
для инженерного вывода. Экспорт JSON содержит `illustration_only: true` и
`physical_solver_used: false`. Настоящие команды проекта доступны в документации
на сайте; выполнение ядра остаётся локальным и отдельным.

## Grid Studio — записанная физика

Открыть `http://localhost:5173/grid.html`. Интерактивная однолинейная схема,
направления P, загрузка линий, напряжения, контакторы и вращение двигателей,
инспектор, осциллограммы, масштабирование, миникарта и воспроизведение.
12 записанных исследований: звезда/цепочка, пуск, ступени, провал,
размыкание и повторное включение каждого двигателя. Стороны pre/post события
различаются без интерполяции. Потоки рассчитаны из комплексных напряжений
и сопротивлений линий; движение штрихов условное. Превышение длительного
номинала тока само по себе не означает срабатывание защиты.

PNG/SVG сохраняют текущую схему. JSON сохраняет только прошлый префикс
наблюдений без будущих команд, тепловой реплики и инженерного вердикта.
Режим агента скрывает эти поля в интерфейсе; это не граница безопасности
и не замена формату обучающего корпуса. JSON можно загрузить обратно;
импорт помечается непроверенным, поскольку браузер не запускает физическую сверку.

Формат `power-grid-env.grid-studio/v1`: максимум12MB,128 узлов на радиальную
схему,256 двигателей,10000 отсчётов. Эти пределы валидатора не являются
измеренным масштабом производительности. Для ручной радиальной сети теперь есть отдельный редактор и локальный API (см. ниже).
Кольцевые схемы, GIS и квалификация больших графов пока не реализованы.

Воспроизведение статического набора из корня проекта:

```sh
python -m benchmarks.export_grid_studio \
  --source reports/three-motor-train-2026-11-17 \
  --source-manifest 313011c1b01545687d1aee6e953c2784d6163ecda722c7172fb775265a936c55 \
  --out web/assets/grid-replays.json
```

Исходный sealed report нужен для повторного экспорта; готовый сайт использует
включённые JSON и manifest. `npm run check` выполняет19 проверок модели данных,
включая стороны событий, импорт и отсутствие будущих данных в экспорте.

## Ручной конструктор и расчёт

Открыть `http://localhost:5173/editor.html` или «Конструктор сети» в Grid Studio.
Добавьте шины, нажмите «Соединить шины» и выберите две шины. Выберите шину
и добавьте двигатель. Оборудование выбирается мышью либо Tab + Enter;
шины перетаскиваются, координаты также редактируются в параметрах.
«Новый проект» создаёт пустую схему с одной шиной источника; начальный пример
содержит два двигателя. Удаление шины удаляет её линии и двигатели;
Undo/Redo позволяет восстановить изменения (Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z).

Редактируются напряжение, эквивалентные R/X источника, длина и R/X на км
кабелей, допустимый ток, kVA/H и электрические pu-параметры двигателей,
вентиляторный момент и время включения. Исходные параметры примерные.
Сохранение/импорт проекта используют `power-grid-env.grid-editor/v5` (v1/v2/v3/v4 мигрируют с явными defaults),
не формат записи расчёта. Незавершённые черновики можно сохранять и открывать;
для расчёта нужна связная радиальная сеть и хотя бы один двигатель.
Черновик автоматически сохраняется в localStorage этого origin; результат
последнего ручного расчёта — в IndexedDB. Очистка данных браузера удаляет их;
для переносимой копии используйте JSON.

«Проверить схему» проверяет также применимость в Python. «Рассчитать и открыть»
запускает существующий `run_induction` (SciPy), затем открывает результат
в Grid Studio. Передача результата остаётся локальной. При необходимости:

```sh
PGE_PYTHON=/home/user/miniconda3/bin/python npm run dev
```

По умолчанию используется `python3` из PATH; ему нужны зависимости проекта.
Запускать из исходного checkout: мост `benchmarks/grid_editor.py` использует
существующий шаблон StudySpec, полностью заменяя сеть и двигатели данными проекта.

Профиль: один источник Тевенина (может включать приведённый Z трансформатора),
50Hz, симметричная сеть: НН100–1000V либо многовольтный RMS100–35000V, до16 шин/16 одно- или двухклеточных двигателей,16 постоянных Z-нагрузок,
опциональная тепловая I²-защита,вентиляторная нагрузка, до10s, шаг выдачи1–2,5ms. Двухобмоточные трансформаторы доступны в многовольтном RMS-профиле.
Сетевых защит,генераторов,островов и несимметрии в редакторе пока нет.
Это один расчёт на выбранной сетке, без независимой проверки сходимости
и без автоматического инженерного вердикта. При включённой I²-защите инженерный вид показывает тепловую реплику;
это не температура обмотки. Агентский экспорт исключает её. Неподдерживаемые сочетания ограничений отклоняются явно.

API принимает только JSON POST `/api/editor/validate`, `/api/editor/solve` и `/api/editor/export`,
проверяет loopback Host и same-origin Origin; внешнего CORS нет. Один процесс
одновременно, вход256KB, время45s, выход12MB; отмена запроса останавливает процесс.
Нет клиентских путей к файлам или произвольного запуска команд.

```sh
npm run check                 #57 JS-проверок + синтаксис/ссылки
npm run check:api             #19 локальных HTTP-проверок, включая SciPy
# из корня checkout:
python -m pytest tests/test_grid_editor.py tests/test_grid_studio_export.py -q
```

Следующая очередь: новые виды оборудования и сценарии, измеренное масштабирование,
многоуровневое напряжение и кольца. Текущие пределы не означают поддержку
произвольной промышленной схемы.

## Инженерное рабочее место и среда агента

Каталог в заголовке содержит16 семейств,включая все equipment-классы формата
Network. Поиск и группы показывают совместимость с текущим профилем. Карточка
неподключённого оборудования объясняет недостающий адаптер; она не добавляет
фиктивный объект. Дерево проекта выбирает объекты независимо от размера схемы.
На широком экране панели прокручиваются отдельно,команды расчёта закреплены.

В профиле motor-start доступны одно/двухклеточный двигатель и тепловая
I²-реплика с отключением,нагрузка постоянного Z (симметричная заземлённая звезда),
и до64 команд: источник U-scale,масштаб механического момента,
отключение/замыкание контактора. Первый пуск задаётся в паспорте.
Противоречивые совпадающие команды,неизвестные цели и времена вне горизонта
отклоняются. Пуск,совпадающий с явной командой контактору,тоже отклоняется.
Ток нагрузки вычисляется из фактического U; P/Q меняются как U².
В Grid Studio нагрузка имеет отдельный символ и инспектор.

«Среда агента» показывает задачи,состояние корпуса и незакрытые критерии.
636 подготовленных SFT views получены из159 префиксов21 трассы; это не столько
независимых сетей. Предыдущий adapter Qwen3.5-0.8B получил9/48 dev и не прошёл
смысловую оценку. Нового обучения в интерфейсных блоках нет.

Целевой процесс: проверенные физические семейства и сценарии → публичная схема,
паспорта,измерения/графики только до текущего t → SFT на ответах и tool traces →
группы самостоятельных действий GRPO с повторным расчётом и независимой оценкой.
Замкнутый physics-scored GRPO и общая tool-policy инженера ещё не реализованы.
Ручной одиночный прогон не становится эталоном: отдельно требуются сходимость,
независимая сверка,параметры с происхождением и разделение по семействам сети,
оборудованию и возмущениям. Публичные наблюдения и oracle/checker хранятся отдельно.

## Многовольтный RMS-профиль и трансформаторы

В селекторе «Профиль расчёта» доступны два реализованных режима:
`lv_motor_start` и `multivoltage_motor_start`. Во втором каждая шина имеет
собственное номинальное линейное напряжение100–35000V. Источник и двигатели
используют базу своей шины. Кабель между разными напряжениями отклоняется;
между такими шинами нужен трансформатор. Смена профиля не удаляет оборудование,
а показывает несовместимость и блокирует расчёт. Пределы:16 шин,16 двигателей,
16 Z-нагрузок,до8 трансформаторов;все линии+трансформаторы образуют дерево.

«Пример ввода10/0,4kV» создаёт редактируемый ввод с400kVA трансформатором и
двумя75kVA двигателями. Это authored пример с предполагаемыми параметрами,
не паспорт производителя. Для ручной сборки нажмите «Трансформатор между шинами»
и выберите две шины на схеме или в дереве. Напряжения задаются в паспортах шин.

Трансформатор:две обмотки,группы Yy0/Dyn11/Dyn1/Dd0,номинальная мощность,
суммарное R% и **реактивное X% отдельно** на номинальной мощности,
фиксированные ответвления обеих обмоток0,8–1,2pu. Величина uk% из паспорта
не должна вводиться как X% без преобразования с учётом R%. Нейтраль задаётся
согласно группе. Намагничивание,потери стали,насыщение,бросок включения,
динамический РПН,трёхобмоточные и автотрансформаторы в этот профиль не входят.

Потоки вычисляются по записанным комплексным напряжениям и фактической
комплексной матрице трансформатора с tap/clock:токи обеих сторон в A,
отдающая/приёмная P,Q,потери меди,максимум |S| сторон / Sном. Передача мощности
в обратном направлении также учитывает реальную сторону обмотки.
На схеме показаны отдельные символы и напряжения шин;инспектор узла показывает
локальное U и угол относительно внешнего источника. Это симметричный RMS,
не фазная/нулевая последовательность и не расчёт токов КЗ.

«StudySpec JSON» сохраняет полное исследование в штатном формате Python-ядра,
включая сеть,паспорта,будущие команды и настройки. Он предназначен для повторного
расчёта и tool-use агента,**не является past-only наблюдением**. Для наблюдения
используйте отдельный JSON-экспорт Grid Studio;он сохраняет статические данные
трансформатора и прошлые измерения,но исключает будущие события/тепловой oracle.
Новые ручные MV-записи не включаются в эталонный SFT-корпус автоматически.

Осциллограммы Grid Studio зависят от выбранного объекта. Для двигателя
сравниваются моторы;для кабеля доступны I,P,Q,потери и загрузка;для
трансформатора I/P/Q обеих сторон;для шины U в pu/V и угол;для нагрузки
P/Q/I/U;для источника P/Q. Ось времени едина. В режиме агента и временной
диапазон,и массивы выбранных каналов ограничены текущим префиксом.

## Статические PF/КЗ и сетевые аппараты

Доступны ещё два профиля: `passive_power_flow` и `passive_3ph_fault`.
В редакторе есть примеры PF с выключателем и трёхфазного КЗ.
Решатель — существующий `backend_opendss` (локально проверены
opendssdirect.py0.9.4/dss-python0.15.7); Python должен иметь зависимости проекта.
Поддерживаются источник,кабели,двухобмоточные трансформаторы,постоянные
Z-нагрузки и статические положения аппаратов. Замкнутые схемы и обесточенные
острова допускаются в PF. В RMS-профилях ограничения дерева сохраняются.

Двигатели и временные команды в этих пассивных профилях **отклоняются**;
автоматической подмены двигателя Z/PQ-эквивалентом нет. Смена профиля не
удаляет их. Временные настройки проекта сохраняются для RMS,но не создают
временную интеграцию PF. Формат проекта v4 мигрирует v1/v2/v3.

Аппарат соединяет две одноимённые по напряжению шины:выключатель или
разъединитель,положение,номинальный ток,явные R/X и паспортные параметры.
В существующем ядре топология сливает замкнутые Switch в узел независимо от
поля representation. Поэтому мост редактора **явно преобразует статический
снимок**:замкнутый аппарат становится Line с его R/X и ID,разомкнутый —
разрывом без ветви. Параметры аппарата сохранены в assumptions StudySpec и
полном JSON-проекте. Это не скрытая нулевая ветвь и не глобальное изменение
поведения Switch в ядре. Native StudySpec повторяет именно этот снимок;
для изменения состава/положения используйте проект редактора.

Профиль КЗ:три фазы через одинаковый конечный импеданс на выбранной шине,
R≥10µΩ, X≥0. Он рассчитывает пассивное воздействие внешнего источника;
нет вкладов двигателей/генераторов,IEC60909 voltage factors,пикового тока,
несимметричных КЗ или переходных коммутаций. КЗ на обесточенной шине явно
отклоняется. Номинальный ток аппарата и отключающая способность не становятся
критерием селективности:показывается только ток через данный выключатель в
этом одном КЗ и его сопоставление с введённой способностью. Для разъединителя
отключение КЗ не оценивается. Никаких автоматических trip/operate-time действий.

Результаты открываются в `steady.html`:схема с положениями аппаратов,
энергизованными/обесточенными узлами,фазные U/углы,потоки и потери ветвей,
фазные токи КЗ и отдельная диагностика. Напряжения фаз — относительно
нейтрали,номинал шины — линейный. На непроводящей/обесточенной ветви
неизвестный ток показан как «—»,не как измеренный ноль. Это статический
снимок без искусственных осциллограмм. JSON результата хранится отдельно
от RMS в IndexedDB и экспортируется с native-study/bridge/core SHA и
версией backend;это не gold SFT или past-only наблюдение агента.

Дополнительные проверки:

```sh
python -m pytest tests/test_editor_steady.py -q
```

## AC PF: законы нагрузок и статические генераторы

Профиль `ac_power_flow` добавляет constant-PQ,constant-I и ZIP-нагрузки,
а также до8 статических генераторов PQ/PV. Старые RMS/пассивные профили
по-прежнему допускают только Z-нагрузки и не принимают генераторы;смена
профиля ничего не удаляет. Пример «AC PF / генерация» содержит PQ/ZIP
нагрузки и генератор150kW с возвратом мощности во внешнюю сеть.

У ZIP отдельные неотрицательные тройки Z/I/P для активной и реактивной
мощности;каждая должна давать1. Для PQ/I/ZIP задаётся диапазон напряжения
применимости. Мост отклоняет завершённый native расчёт,если напряжение
вышло из окна и OpenDSS мог перейти на импедансный эквивалент. Дополнительно
проверяются P/Q по фактическим фазным U и объявленному закону,отклонения
доступны в инспекторе нагрузки. Численная сходимость сама по себе не
считается соблюдением заявленной модели. Обесточенная нагрузка не получает
фиктивных измерений и проверки закона.

PQ-генератор задаёт выдаваемые P/Q,PV — P/U и Qmin/Qmax. Номинальные kVA
ограничивают допустимые задания/пределы,но это не модель перегрузки машины.
Фактические P/Q,напряжение,ошибка задания U и Q-предел показаны отдельно.
Нативная диагностика близости к Q-пределу отличена от проверки фактического
достижения границы. Для выбранного адаптера рабочее окно генератора
фиксировано0,9–1,1pu;вне него результат отклоняется,чтобы не принять
скрытый fallback. Командные P/Q также сверяются с фактическими.

Это стационарный эквивалент,не динамика синхронного ротора/AVR. Генератор
PQ/PV не формирует остров:при потере внешнего питания его измерения
отсутствуют,напряжение не выдумывается. Вклад генератора в КЗ не оценивается;
такой проект в пассивном fault-профиле отклоняется явно.

В `steady.html` добавлены символ/инспектор генератора и инспектор нагрузки,
таблица «Нагрузки / генераторы» с фактическими P/Q/I. Положительная P
внешней сети означает питание площадки,отрицательная — экспорт.
Положительные P/Q нагрузки означают потребление,генератора — выдачу;
отрицательная Q генератора означает поглощение. Native StudySpec содержит
настоящие load laws/Generator объекты. Новые записи не являются gold SFT.

### Локальный Qwen tool-loop

`benchmarks.engineering_rollout` — owner-run цикл: на вход candidate-процесса
поступают только публичные сообщения, на выходе одно действие

ответ нельзя зачесть другому заданию. Отчёты пишутся только в новый каталог

### SFT loader и квалификация адаптера

`benchmarks.engineering_sft` проверяет owner manifest и повторно исполняет
каждую train-траекторию. Подставленные наблюдения, dev/test и неполные
траектории отклоняются. Native processor заново проверяет точное продолжение
токенов; вход маскируется -100, loss считается только по assistant-completion.
Сейчас поддержан batch-size=1 без padding, truncation и packing.

Из корня проекта (укажите новый каталог вывода):
```bash
.venv-qwen35-08b/bin/python -m benchmarks.engineering_sft \
  --target requirements/qwen35-08b-local-target.json \
  --target-sha256 e763c82b7f4f1d5acea273b43674e45bcdb949fc91d000cb7537ea54b5fa0262 \
  --corpus reports/engineering-action-supervision-2026-11-17 \
  --manifest-sha256 fbb8d175acaa4dfe8f2bcfe36cbaf3d009bbdf6ce8c2c01d603cb1c601ccc220 \
  --out reports/action-sft-NEW --train-step
```
Без `--train-step` выполняется только проверка всех батчей, без весов.
С флагом — ровно один шаг rank4 LoRA на `--index` (по умолчанию 0), проверка
неизменности базы и точного adapter roundtrip. Это qualification, не полный
SFT epoch. Результат содержит `adapter.safetensors`, план и manifest.

receipt должен соответствовать выбранной модели. Worker проверяет совместимость
модулей и весов, исходный checkpoint остаётся read-only. Не смешивайте train loss
на одном примере с качеством решения dev-задач. Полный schedule, optimizer resume,
сравнение base/adapter на одинаковом бюджете, визуальные входы и GRPO впереди.

### Полный action-SFT epoch и возобновление

`benchmarks.engineering_train` формирует детерминированную перестановку всех
38 примеров для каждой эпохи. Обучение использует тот же проверенный loader,
семь rank4 LoRA-проекций последнего decoder block и masked causal loss.
По умолчанию — один epoch, seed42, AdamW lr0.0002, batch-size1, CPU float32.
Это небольшой provisional teacher-корпус, а не доказательство качества агента.

```bash
.venv-qwen35-08b/bin/python -m benchmarks.engineering_train \
  --target requirements/qwen35-08b-local-target.json \
  --target-sha256 e763c82b7f4f1d5acea273b43674e45bcdb949fc91d000cb7537ea54b5fa0262 \
  --corpus reports/engineering-action-supervision-2026-11-17 \
  --manifest-sha256 fbb8d175acaa4dfe8f2bcfe36cbaf3d009bbdf6ce8c2c01d603cb1c601ccc220 \
  --out reports/action-epoch-NEW
```

`--max-steps 2` останавливает chunk после двух новых шагов и сохраняет
адаптер, AdamW moments/step и CPU RNG в safetensors без pickle. Receipt содержит
полный порядок примеров, курсор, историю и identity кода/модели/корпуса.
Для продолжения добавьте `--resume PATH --resume-manifest-sha256 SHA` и новый
`--out`; seed/epochs и identity должны совпасть. Завершённый schedule повторно
возобновить нельзя. Проверка точного непрерывного/раздельного обновления
AdamW выполняется тестом в текущем CPU-профиле; перенос между версиями
библиотек или аппаратными платформами не квалифицирован. Автоматического
checkpoint на каждом шаге нет: сохранение происходит в конце заданного chunk.

Worker допускает законченный epoch-adapter с `schedule_complete:true`.
Промежуточный checkpoint предназначен для trainer resume и не принимается
как законченный адаптер для сравнения. Исходные веса не перезаписываются.
