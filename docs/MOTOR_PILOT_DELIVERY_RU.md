# Воспроизводимая поставка профиля пуска и самозапуска двигателей

Целевой первый профиль, выбранный пользователем: офлайн-пуск и самозапуск
двигателей промышленной сети. Это текущий приоритет внутри общей цели
промышленного моделера; широкая библиотека моделей и сетей остаётся общей целью.
Экономическая часть не рассматривается.

## Текущий критерий готовности

Промышленный статус не выводится из числа тестов. Для целевого оборудования
нужны паспорта, схема, импедансы сети, модель механизма, стартовые состояния,
записи U/I/скорости с временной шкалой, независимые контрольные случаи и
протокол приёмки. Эти данные пока не предоставлены. Синтетические примеры
не объявляются натурными измерениями или заводской квалификацией.

Следующий завершённый инженерный блок — переносимое исследование и
проверка установки из wheel. Он закрывает часть воспроизводимости P3,
но не подменяет P1/P2/P4/P5, независимую другую машину и инженерную приёмку.

## Motor bundle

Новые команды для `motor_start/scipy`:

```bash
python3 -m power_grid_env.cli motor-bundle create --study cases/studies/thermal_cold_trip.json --criteria cases/replay/motor-start.json --trace cases/measurements/synthetic_motor_cold_trip.csv --trace-protocol cases/measurements/synthetic_motor_cold_trip.protocol.json --out /tmp/motor-bundle
python3 -m power_grid_env.cli motor-bundle verify /tmp/motor-bundle --out /tmp/bundle-verification.json
python3 -m power_grid_env.cli motor-bundle replay /tmp/motor-bundle --out /tmp/bundle-replay.json
```

Создаётся обычный каталог с фиксированным inventory:
`study.json`, `result.json`, `criteria.json`, `environment.json`, `manifest.json`.
При сверке также включаются `trace.csv`, `trace-protocol.json`, `comparison.json`.
Trace и protocol передаются вместе. Входной CSV копируется и сверяется именно
в сохранённом виде, без повторного чтения меняющегося исходника.

Пакет хранит SHA-256 файлов, fingerprint кода и runtime identity: Python,
Linux/архитектура, версии 22 runtime-дистрибутивов и настройки числа BLAS threads.
Это идентификация версий/настроек, не полная аттестация бинарного окружения;
для зафиксированной установки используются wheel hashes lock-файла ниже.
Полная исходная папка проекта не нужна: wheel и явные данные достаточны.

Проверка отклоняет лишние/отсутствующие файлы, symlinks и вложенные каталоги,
плохой inventory/checksum, неподдержанный профиль, неверные event time/discrete
channels, несовпавший код или runtime, неоднозначный JSON и попытку повысить
флаги квалификации. Чтение ограничено 64 MB на обычный файл, 256 KB на manifest,
суммарно 128 MB. CSV дополнительно ограничен существующим 32 MB контрактом.
Каталог создания должен быть новым/пустым. Manifest публикуется последним;
незавершённый расчёт не получает sealed-пакет. Нельзя записать output
проверки/replay внутрь неизменяемого bundle через CLI.

Worker теперь запускается из отдельного временного каталога с путём к пакету,
загруженному родительским процессом. Это исправляет зависимость импорта от
текущего рабочего каталога; killable subprocess остаётся trusted-local worker,
не OS sandbox или memory quota.

## Что именно проверяет replay

[Явный протокол](../cases/replay/motor-start.json) фиксирует до запуска допуски
по времени, pu-каналам, мощности W/var, углам rad и thermal level, а также
wall deadline. Дискретные connected/latch требуют точного равенства.
Сравниваются все сохранённые каналы, их inventory, число/стороны отсчётов и
аудит событий с допуском времени. Для угла используется круговая разность.
При иной структуре сетки результат отклоняется, а не подгоняется интерполяцией.
Изменение manifest во время replay тоже отклоняется.

`repeatable` — повторяемость заявленных численных выходов. Это отдельно от
`measurement_comparison_passed` по заранее заданному CSV-протоколу.
Неуспешную CSV-сверку можно сохранить и воспроизвести; это важно для честного
разбора неуспешных пусков. CLI возвращает 2 при нарушении repeatability или
явном непрохождении CSV-допусков; sealed-статус не превращает их в pass.
Отсутствующая CSV-сверка не становится натурной валидацией.

Hashes не удостоверяют происхождение измерений: `provenance_authenticated`,
`field_validated`, `industrial_profile_qualified` остаются false. Bundle
снабжает инженерную приёмку воспроизводимыми входами/выходами, но не выдаёт
сам себе инженерное одобрение. Поддержка coupled_rms в этом bundle-профиле
пока не заявлена; его обычные StudySpec/CLI продолжают работать отдельно.

## Зафиксированная установка

[Runtime lock](../requirements/pilot-linux-py312.lock) фиксирует 22 wheel-дистрибутива
и SHA-256 для Linux x86_64 / CPython 3.12. Обнаруженная несовместимость рабочей
среды `typing-inspection 0.4.4` / `typing-extensions 4.14.1` устранена в
новом lock выбором `typing-extensions 4.15.0`; рабочая среда пользователя
не обновляется автоматически.

Подготовка wheelhouse и проверка:

```bash
python3 -m pip download --only-binary=:all: --require-hashes -r requirements/pilot-linux-py312.lock --dest /tmp/pge-wheelhouse
python3 -m benchmarks.pilot_installation --work /tmp/pge-install-work --out /tmp/pge-install-report --wheelhouse /tmp/pge-wheelhouse
```

Сборка использует локальные setuptools/wheel с записанными версиями,
`--no-build-isolation --no-deps` и фиксированным SOURCE_DATE_EPOCH.
Две сборки должны дать одинаковый wheel SHA на этом host. Далее создаются
два отдельных venv без system-site-packages. Все runtime wheels и wheel проекта
устанавливаются offline с `--require-hashes`; `pip check` обязателен.
Импорт, OpenDSS smoke и motor bundle replay выполняются с `python -I` из
пустых рабочих каталогов. Явно проверяются installed-package path внутри venv,
отсутствие repo root в sys.path, совпадение кода и повторяемость в обоих venv.

В CI добавлена отдельная job `motor-wheel-replay`. Она не требует ANDES:
это motor_start/scipy плюс базовый PF smoke. Linux/Python 3.11 source-тесты
не превращаются этим lock в квалификацию wheel для Python 3.11/ARM/Windows/macOS.

[Сохранённая проверка чистых venv](../reports/motor-pilot-runtime-2026-10-31/qualification.json).
[Сводка регрессии и поставки](../reports/motor-pilot-runtime-2026-10-31/delivery.json).
Два venv на одном host — существеннее импорта с унаследованными зависимостями,
но это всё ещё не независимая другая машина. Synthetic CSV подтверждает
реализацию протокола и численную повторяемость, не реальную точность мотора.

## Методическая очередь до промышленного профиля

1. Сохранить и проверять текущий runtime/артефактный контракт, получать
   независимое повторение пакета на целевой машине.
2. Получить профиль целевого привода: схемы питания/контакторов, паспорт и
   параметры эквивалентной схемы мотора, инерция/нагрузка, пусковые ограничения,
   OEM thermal/protection и параметры холодного/тёплого состояния.
3. Провести внешний динамический benchmark и benchmark группового пуска
   с измерением времени/пиковой памяти на объявленных размерах; отделить
   нелинейную несходимость и физический неуспех пуска от resource failure.
4. Зафиксировать матрицу успешных/неуспешных пусков, провалов и самозапусков,
   диапазоны/корреляции параметров, независимые held-out измерения и допуски.
5. Закрыть необходимые именно для объекта пробелы механики, тепловой защиты,
   контакторов и автоматики. Single-cage не подменяет насыщение/deep-bar/VFD.
6. Независимая инженерная приёмка, release-кандидат с lock/артефактами,
   подтверждение границ применения и регламент обработки отказов.

Широкий промышленный моделёр дополнительно требует объявленных островов,
синхронизации, converter/GENSAL/прочих моделей и внешнего многосемейного
корпуса. Эти задачи не отменены выбором первого профиля. До выполнения
ворот статус — engineering prototype/candidate, industrial release=false.
