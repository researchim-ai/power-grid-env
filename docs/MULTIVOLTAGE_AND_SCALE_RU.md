# Многовольтный RMS, корректный PV и масштаб сети

Следующая реализация поверх общего RMS adapter. Промышленный профиль,
натурная точность и превосходство над другими инструментами не объявлены.

## Двухобмоточные трансформаторы в общем RMS

`StudySpec rms/andes` теперь переносит сеть с разными уровнями напряжения,
а не назначает всем узлам одну номинальную базу.

Поддержанный subset:

- симметричные трёхфазные двухобмоточные трансформаторы;
- явные равные MVA-номиналы обмоток, заданные leakage X и load losses R;
- две явные winding R либо общий load-loss percentage;
- отпайки обеих обмоток, отличающиеся от единицы;
- векторные группы 0/1/5/11 в проверенных cases;
- явно нулевые magnetizing current и no-load losses;
- фиксированные отпайки без LTC dynamics.

Несимметрия, нулевая последовательность, насыщение/inrush, трёхобмоточная
модель, частично заданные winding resistances и динамическое регулирование
пока отклоняются этим adapter. Они не подменяются «похожим» эквивалентом.

Каждая шина/нагрузка/генератор/линия использует свою voltage base.
Transformer переводится в ANDES complex-tap branch на согласованной базе.
Серия учитывает LV tap, а отношение taps задаёт комплексный коэффициент.
Угловая начальная оценка учитывает clock, чтобы flat start не уводил PF
далеко от решения для 150-градусной группы.

Проверены:

- YNyn0, Dyn11, YNd1, Dyn5 и YNd5;
- отпайка НН и отдельно отпайка ВН;
- смена системной MVA-базы и explicit winding R;
- PF модули/углы против фазного OpenDSS;
- физическое SI-уравнение transformer+line+PQ load с независимым root;
- динамическая реакция на ступень нагрузки.

Пример после установки RMS extra:

```bash
python -m power_grid_env.cli run-study cases/studies/rms_multivoltage.json \
  --out /tmp/rms-multivoltage.json
```

## Исправлена фазировка clock-5 в OpenDSS adapter

Раньше группа 5 проходила через default LeadLag и давала неверную фазировку:
модуль мог совпадать, а угол отличался на 120°. Теперь ANSI -30° сочетается
с явной циклической перестановкой терминалов НН на -120°. Node order остаётся
частью электрической модели, а токи читаются по фактическому номеру узла.
Для phase-specific/explicit-node winding такого неявного преобразования нет:
эта комбинация отклоняется.

Новая проверка сопоставляет не только два adapter, но и физическое уравнение
с заранее заданными углами 0°, +30°, -30° и -150°. Ошибка угла не прячется
в допуск модуля напряжения.

## Исправлены PV setpoint и bounded refinement

[Документация DSS-Extensions Generator](https://dss-extensions.org/dss-format/Generator.html)
разделяет `Vpu` (уставка Model 3) и `VMinpu/VMaxpu` (диапазон применимости).
В каноническом Generator они теперь также отдельны: `v_set_pu`, `v_min_pu`,
`v_max_pu`. Для новых объектов диапазон по умолчанию 0.9…1.1 pu;
импорт с явным Vpu сохраняет заданный диапазон. Старые файлы репозитория с
равными vmin/vmax и без Vpu читаются как legacy convention с сохранением band.
Неопределённая уставка не угадывается.

Если первый native solve PV не сошёлся, выполняются ограниченные повторные
Solve на **полной исходной нагрузке**. `max_pv_refinements` в SolveOptions
задаёт бюджет 0…32 (по умолчанию 4). Учитывается каждая попытка. Если load
continuation завершился раньше, перед возвратом обязательно восстанавливаются
исходные уставки и выполняется solve исходной модели. Reduced-load operating
point больше не выдаётся как результат запроса исходной нагрузки.

Допуски PQ 1e-5 и KCL 1e-8 pu не ослаблены. Двух-PV mesh-case теперь сходится,
сохраняет исходную нагрузку и совпадает с ANDES PF. Отсутствие сходимости всё
так же не обозначает физический collapse.

## Масштаб: проверка результата стала линейной

При распределённой нагрузке обнаружен квадратичный проход: для каждой
нагрузки просматривались все voltages и flows. Он заменён однократным
индексированием по bus/equipment с теми же проверками применимости PQ band,
пофазных мощностей и исходными допусками. Изменяется стоимость проверки,
а не уравнения и не физика результата.

Воспроизводимый benchmark:

```bash
python -m benchmarks.scale_networks --sizes 100 1000 10000 --repeats 3 \
  --out /tmp/branching-scale
```

Семейства: binary-tree radial и tree с дополнительными mesh ties;
500 W + 100 var на каждой нерoot шине, явные impedances и один источник.
Мощность/число нагрузок действительно растут с числом узлов. Это синтетические
balanced networks, не реальные города и не всякая промышленная площадка.

Сохраняются raw wall times, build time, process-lifetime peak RSS (Linux KiB),
число каналов и пропущенного оборудования, PQ/KCL residuals, интегральный
баланс мощностей и статус каждого повторения. Первый solve может включать
native startup; raw values не объединяются в заявление о steady-state p95.

[Результаты](../reports/branching-scale-indexed-2026-10-30/summary.json).
Предыдущая попытка до индексации на 10 000 узлах остановлена; её неполный
набор raw результатов не является завершённым envelope.

Этот эксперимент не имеет независимого oracle для большой сети и не
доказывает «любые масштабы». Большие несимметричные схемы, mixed equipment,
контроллеры/QSTS/RMS и пределы памяти требуют отдельных workloads.

## Следующая очередь

1. Расширять equipment/task/backend coverage по независимым reference cases.
2. Добавить общие AVR/governor/PSS contracts, затем fault/clearing и motors.
3. Проверять крупные asymmetric и mixed-voltage cases, длинные production
   QSTS и ресурсный budget parent+workers отдельно.
4. Профилировать импорт, сборку, выдачу результатов и IO так же, как solver.
5. Публиковать matched comparison только после accuracy gates, вместе с
   failure cases и ограничениями, а не по лучшему выбранному примеру.


## Полученный ресурсный результат

В серии из трёх повторов все 6 сочетаний size/family прошли. Для 10 000
узлов raw full-solve times составили около 19.6–29.1 s, process-lifetime RSS
peak около 812 MiB. Включены сборка/solve/read/валидация внутри solve_network;
построение canonical Network измерялось отдельно. Данные не являются p95 SLA
или результатом сравнения с другим продуктом.

После отдельного изменения exact-mode guard сделан дополнительный прогон
10 000 узлов на финальном source hash:
[финальная проверка](../reports/branching-scale-final-2026-10-30/summary.json).
Source fingerprints у raw серий сохранены раздельно; не подменять их хешем
последней версии. Full qualification release остаётся закрыт.
