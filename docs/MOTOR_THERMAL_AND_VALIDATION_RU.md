# Тепловая память, отключение двигателя и сверка с трассами

Дополнение к [динамическому motor study](INDUCTION_MOTOR_RU.md): опциональная
токовая тепловая реплика, отключение по пересечению порога и отдельная
команда сверки I/U/скорости с CSV. Промышленный профиль остаётся закрытым.

## Модель защиты

В `induction.motors[].thermal` явно задаются:

```json
{"model":"stator_i2_replica","time_constant_s":1.0,"trip_level":5.0,"initial_level":0.0}
```

Это **синтетический пример параметров**, не рекомендуемые уставки оборудования.
Модель добавляет одно состояние θ на защищённый двигатель:

```text
dtheta/dt = (abs(I_motor_pu)^2 - theta) / time_constant_s
```

Ток взят из того же сетевого решения, что момент и мощность. θ=1 — равновесный
нагрев при номинальном RMS-токе на собственной VA-базе двигателя.
θ не выражена в градусах и не является процентом использованного теплового
ресурса. Порог задан отдельно; отношение θ/trip_level можно интерпретировать
как долю порога этой реплики. Начальный уровень должен быть неотрицательным
и строго ниже порога. Тёплый запуск имеет меньший доступный запас, чем холодный.

Время отключения определяется положительно направленным пересечением θ-порога
в непрерывном решении Radau, не округлением до периода сохранения результата.
Электрический контактор размыкается, но поток ротора, скорость и θ непрерывны.
После отключения ток нулевой, поток затухает, вал выбегает, θ охлаждается.
Для численно совпавших порогов группы отключения применяются совместно;
допуск совпадения ограничен машинным округлением, а не широким допуском ODE.

Защита **защёлкивается до конца исследования**. Плановая команда `motor_close`
после trip не включает двигатель, даже если он уже остыл: журнал содержит
`blocked_thermal_latch`. Автоматический сброс, разрешение повторного пуска
после охлаждения и команда ручного reset пока не реализованы. Команда открытия
уже отключённого защитой двигателя фиксируется как `already_in_requested_state`.

В отчёт добавлены каналы `<motor>.thermal_level`, `<motor>.thermal_latched`,
сводка `motor_summary.<motor>.thermal` и `event_log`. У отключения есть
`time_s`, `equipment_id`, фактический уровень, порог и результат `latched_open`.
Время события записывается до/после коммутации по тем же правилам, что и
остальные события motor study. `completed=true` означает завершение расчёта;
двигатель при этом может быть отключён защитой.

## Запуск и независимая проверка

```bash
python3 -m power_grid_env.cli run-study cases/studies/thermal_cold_trip.json --out /tmp/cold.json --isolate --wall-timeout 30
python3 -m benchmarks.thermal_motor_reference --out reports/motor-thermal-2026-10-30
python3 -m pytest -q tests/test_motor_thermal.py tests/test_motor_trace.py
```

Примеры: [холодный trip](../cases/studies/thermal_cold_trip.json),
[тёплый trip](../cases/studies/thermal_warm_trip.json),
[без отключения](../cases/studies/thermal_no_trip.json),
[запрет повторного включения](../cases/studies/thermal_blocked_reclose.json).

[Сверка четырёх сценариев](../reports/motor-thermal-2026-10-30/reference.json)
использует независимую SI-модель потокосцепления ротора, отдельные уравнения
токов статора/ротора и DOP853 с терминальным поиском порога. Сравниваются
скорость, θ, ток, напряжение и время trip; допуск времени — 1e-6 с.
Скачки сравниваются на соответствующих до/после пределах, а ошибка времени
события проверяется отдельно. Дополнительно проверяются точные выражения
нагрева/охлаждения при постоянном токе и времени пересечения, асимптотический
порог без конечного trip, шаг/полушаг, группа и отдельный worker.

## Сверка CSV с расчётом

Публичная команда принимает сохранённый расчёт и отдельный протокол:

```bash
python3 -m power_grid_env.cli compare-motor-trace \
  --study cases/studies/thermal_cold_trip.json \
  --result /tmp/cold.json \
  --trace cases/measurements/synthetic_motor_cold_trip.csv \
  --protocol cases/measurements/synthetic_motor_cold_trip.protocol.json \
  --out /tmp/comparison.json
```

[Пример CSV](../cases/measurements/synthetic_motor_cold_trip.csv) получен из
независимого SI-эталона и явно помечен как синтетический. Это проверка пути
сверки, **не измерение реального двигателя**.

CSV содержит ровно четыре именованных столбца (порядок допустим любой):
`time_s,current_a,voltage_ll_v,speed_pu`. Ток — RMS линейного тока, напряжение —
RMS линейного напряжения **шины присоединения**, скорость — доля синхронной
механической скорости. Произвольные фазные осциллограммы и температура обмотки
не принимаются как эти каналы. Если запись содержит rpm, её нужно явно
перевести по частоте и числу пар полюсов с сохранением происхождения данных.

[Протокол](../cases/measurements/synthetic_motor_cold_trip.protocol.json)
фиксирует study/motor ID, dataset ID, источник, объявленный вид данных
(`synthetic_reference`, `published_reference`, `field_measurement`), SHA-256
байтов CSV, использование при подборе параметров, временной сдвиг,
максимальный интервал между отсчётами и абсолютные допуски I/U/скорости в SI.
JSON Schema выгружается командой `schemas` как `motor-trace.schema.json`.

Правила сравнения:

- Не менее трёх конечных отсчётов; время строго возрастает; RMS-ток и напряжение
  неотрицательны. Данные должны покрывать ровно весь горизонт, без пропусков
  сверх заранее объявленного интервала. Интервал выборки выбирается для
  исследуемого переходного процесса, а не по удобству получения pass.
- Только явно заданный временной сдвиг; поиска лучшего лага и автоматической
  подгонки нет. У начала/конца допускается лишь округление времени до 1e-9 с.
- При точном совпадении со временем коммутации используется послеаварийный
  (`post_event`) предел. Между событиями интерполяция линейная; скачок через
  одинаковую временную метку не усредняется.
- Полнота, ID, настройки, network hash и актуальный code hash расчёта проверяются
  до метрик. Изменённый CSV, NaN, неверные единицы/колонки, отсутствующий канал,
  устаревший или незавершённый расчёт не превращаются в успешную сверку.
- Для каждого канала сохраняются максимальная абсолютная ошибка, RMSE,
  фиксированный допуск и pass/fail. Код CLI — 0 при прохождении всех каналов,
  2 при отказе входа или превышении допуска.

Успех сравнения не подтверждает подлинность источника, независимость выборки
или корректность калибровки измерителя. Эти свойства требуют отдельной
проверки. `provenance_authenticated`, `field_validated` и
`industrial_profile_qualified` остаются false, даже если протокол объявлен
`field_measurement`. Использованные при настройке модели данные не следует
выдавать за held-out проверку. Сам протокол и семантическое содержимое расчёта
включены в хеши результата; это проверяемый след, а не доказательство времени
предрегистрации протокола.

## Что ещё нужно для промышленного применения

Реплика учитывает один положительно-последовательный ток, постоянное
сопротивление и одну постоянную времени нагрева/охлаждения. Нет отдельной
температуры ротора и статора, skin effect, отрицательной последовательности,
изменения охлаждения со скоростью, ambient/RTD и соответствия конкретному
терминалу защиты. Для реальной моторной защиты нужны заводские характеристики
и пределы — см. [первичный материал SEL о моторных тепловых моделях](https://selinc.com/api/download/3480/).
Текущие четыре случая и параметры синтетические, без OEM- или натурной
квалификации. Не следует переносить точность численной сверки на физическую
точность модели оборудования.

Ближайшие доработки: идентификация по разрешённым данным реального двигателя,
подтверждение выбранной механической характеристики,
отдельные роторный/статорный тепловые контуры и reclose/reset логика, затем
совместная DAE двигателей и синхронных машин. VFD/GFL/GFM и универсальные
islanding/EMT задачи остаются отдельными этапами.

Добавлена [нагруженная инициализация](MOTOR_OPERATING_POINT_RU.md) с явным
выбором начального теплового состояния: из паспорта либо из токового равновесия.
Это закрывает реализацию инициализации, но не OEM- или натурную квалификацию.
