# B17 — идентификация при шуме и ошибках датчиков

Новый режим дополняет динамическую идентификацию B15 контролем невязок по
**исходным** наблюдениям. Пиковая ошибка сама по себе может пропустить небольшой
постоянный сдвиг или дрейф датчика. Теперь эти признаки проверяются отдельно;
непринятый кандидат не получает `passport.json`.

```sh
python -m power_grid_env.cli audit-dynamic-motor \
  --input cases/noisy-identification/linear-noise.json --out /tmp/noise-audit
python -m power_grid_env.cli audit-dynamic-motor \
  --input cases/noisy-identification/linear-speed-filter.json --out /tmp/filtered-audit
python -m power_grid_env.cli audit-dynamic-motor \
  --input cases/noisy-identification/heldout-current-bias.json --out /tmp/rejected-audit
```

Последний пример должен завершиться кодом 2: расчёт выполнен, но качество
исходных наблюдений не принято. Он специально показывает сдвиг проверочного
токового канала, который укладывается в старое максимальное ограничение B15,
но нарушает новый критерий среднего. Положительные случаи завершаются кодом 0.
Каталоги должны быть новыми. Все входы синтетические, не записи оборудования.

## Протокол и критерии

`power-grid-env.dynamic-identification-audit/v1` содержит:

- `identification`: полный строгий документ B15 с `fitting` и `validation`;
- `training_speed_filter_window`: 0 (по умолчанию), 5, 9 или 17;
- `residual_limits`: положительные детерминированные ограничения
  `maximum_mean_sigma` (0.5), `maximum_rms_sigma` (1.5),
  `maximum_half_window_drift_sigma` (1.0). Максимум каждого — 5.

Для каждого исходного канала iα, iβ и механической скорости вычисляется
`e = (свободный расчёт − исходное наблюдение) / sigma`. Проверяются:

1. Максимум |e| не выше `identification.tolerance_sigma` — прежний пиковый предел.
2. |Среднее e| не выше `maximum_mean_sigma`.
3. RMS(e) не выше `maximum_rms_sigma`.
4. |Среднее второй половины − среднее первой| не выше
   `maximum_half_window_drift_sigma`. Для нечётного числа отсчётов вторая
   половина содержит на один отсчёт больше.

Все каналы всех тренировочных и проверочных записей должны пройти **все**
критерии. Кроме этого сохраняются условия B15: сходимость, ранг/разрешимость,
границы параметров, согласованная механика и свободный hold-out. Успешный
RMS токового fit не заменяет эти требования.

Это инженерные пределы в масштабе ошибок, заданном автором, **не** p-value,
проверка нормальности, доверительные интервалы или доказанная вероятность
правильности паспорта. Нельзя увеличивать sigma или подбирать пределы по
проверочной записи, а затем называть её независимой. Смещения, задержки и
ошибки gain в этом режиме не оцениваются как неизвестные параметры. Критерии
могут выявить часть таких несогласованностей, но не гарантируют обнаружение
любой ошибки датчика или структурной ошибки модели.

## Явная обработка скорости

При ненулевом окне применяется квадратичный Savitzky–Golay (`mode=interp`)
**только к тренировочной скорости**. Время должно быть равномерным с
`rtol=1e-7`, `atol=1e-12 s` для шагов; иначе запрос отклоняется. Первый
исходный отсчёт скорости сохраняется: он задаёт начальное физическое состояние.
Фильтр не заменяет известное начальное состояние его оценкой.

Токи и напряжения не фильтруются. Проверочный набор не изменяется и не
используется для оценки параметров. После подбора весь набор заново свободно
воспроизводится найденным паспортом, причём итоговые критерии считаются по
**необработанным** данным. Сглаживание не может само по себе уменьшить шум
наблюдений, относительно которых принимается результат. Это отдельный
явный эксперимент, а не автоматически «улучшенный» метод. Без обработки
и с обработкой сравниваются одинаковые реализации шума.

Наблюдения после CSV-импорта B16 можно использовать как `identification`
аудит-протокола. Исходный пакет B16 следует проверить до формирования запроса;
его происхождение/хеши уже входят в трассы. Внутренние Python-модули для
подготовки такого JSON изменять не нужно. JSON Schema экспортируется командой
`schemas` как `dynamic-identification-audit.schema.json`.

## Артефакты, лимиты и серии

Выход содержит исходный `study.json`, фактический `fit-input.json`, результат,
автономный HTML с графиками и метриками, манифест и принятый паспорт только
при общем успехе. В `result.json`:

- `fit_passed` — приёмка B15 на фактическом входе подбора;
- `raw_residuals_passed` — новая проверка исходных наблюдений;
- `passed` — оба условия выполнены;
- `fit_assessments` — прежние оценки до сырого replay;
- `assessments` и `trajectories` — итоговый свободный replay исходных данных;
- `fit_dataset_sha256`, `raw_identification_sha256`, `audit_protocol_sha256`
  позволяют различать обработанный набор, исходный протокол идентификации
  и полный протокол аудита;
- `preprocessing` сохраняет точные настройки, `residual_limits` — пределы.

Поле `dataset_sha256` унаследовано от B15 и относится к фактическому набору
подбора; оно совпадает с `fit_dataset_sha256`. Кандидат в `result.json` может
сохраняться при отказе и не является принятым паспортом. Паспорта, прошедшие
аудит, дополнительно ссылаются на хеш его протокола.

Число RHS учитывает подбор **и дополнительные raw-replay**. Время аудита
ограничено тем же wall budget; проверяется кооперативно при RHS. Как и B15,
подготовка/публикация артефактов не являются жёстким ОС-таймаутом. Для внешних
ограничений процессов используется `campaign` с новым
`kind: dynamic_identification_audit`. Его `study` содержит документ аудита.
Успех серии требует `passed`, `identifiable`, `fit_passed` и
`raw_residuals_passed`; противоречивые флаги успехом не считаются.

## Воспроизводимая приёмка

```sh
OPENBLAS_NUM_THREADS=1 PYTHONPATH=.:/path/to/pinned-motulator \
python -m benchmarks.noisy_identification_acceptance \
  --wheel /path/to/motulator-0.19.0-py3-none-any.whl \
  --out /tmp/new-noise-acceptance
```

Корпус и пределы полностью сохраняются **до первого подбора**:

- четыре закреплённых исходных B15-набора: линейный и насыщенный вентилятор,
  насыщенный вязкий привод, заторможенный двигатель;
- два seed, 17001 и 17002; PCG64 и SeedSequence([seed, split, trace]) дают
  воспроизводимые отдельные потоки по наборам и записям;
- добавленный Gaussian шум: 0.001 A на каждый токовый канал и 0.001 rad/s
  скорости; начальная скорость известна точно, заторможенный ротор остаётся
  нулевым. Напряжения и потоки в этом корпусе известны без ошибок;
- масштабы приёмки заданы отдельно: 0.004 A и 0.01 rad/s; это консервативные
  инженерные масштабы, не стандартные отклонения с доверительной гарантией;
- окна 0 и 9: 16 положительных сочетаний, предварительный относительный
  предел ошибки истинных параметров 0.02;
- рабочий бюджет 4000000 RHS на подбор вместе с raw-replay, остальные лимиты
  B15 сохранены. Предварительный прогон с 2000000 RHS корректно отказал двум
  случаям; отдельная диагностика показала потребность до 2734735 RHS.
  Увеличен только ресурсный бюджет, а не точностные/невязочные допуски;
- два отрицательных опыта: смещение hold-out iα на 0.004 A и линейный дрейф
  hold-out скорости от 0 до 0.03 rad/s; требуется успешная старая приёмка и
  отказ новой, чтобы проверять дополнительную пользу критериев;
- для первого seed оба варианта обработки всех четырёх профилей переносятся
  в сеть. Восемь расчётов сравниваются с заново выполненной независимой
  motulator/MNA-реализацией с истинным паспортом. Допуски заранее заданы:
  0.1 A, 0.1 V, 0.001 Vs, 0.1 rad/s, 0.1 Nm, 3 W;
- параллельная серия из двух положительных и одного отрицательного случая,
  ZIP-перенос и точное повторное использование успешных результатов.
  Отклонённый случай по правилам campaign рассчитывается заново: все поля
  результата должны совпасть, кроме времени выполнения `elapsed_s`.

Входные электромеханические наблюдения берутся из сохранённого независимого
motulator-корпуса, основной RHS для их генерации не используется. Сетевые
эталоны здесь действительно рассчитываются исходным motulator заново;
wheel проверяется по закреплённому SHA-256. Время параллельного запуска
не используется как сравнительное заявление о производительности.

Два seed и четыре семейства не доказывают универсальную устойчивость к шуму.
Случаи реальных неодинаковых clock, неизвестных потоков, температур, Gc,
многоклеточных машин и шума напряжения требуют отдельных протоколов. B17
не превращает ограниченный профиль в универсально квалифицированную модель.

## Завершённый протокол 8 ноября 2026

`reports/noisy-identification-qualified-final-2026-11-08/summary.json` принимает
16 положительных и два отрицательных случая, восемь независимых сетевых сверок
и восстановление смешанной серии. Максимальная наблюдавшаяся относительная
ошибка параметров — 1.84e-4 в этом синтетическом корпусе; это не гарантия
ошибки на произвольных данных. Сопоставление одинаковых реализаций шума при
окнах 0/9 сохранено отдельно в `processing-comparison.json` локальной поставки.

Полный обязательный профиль: 1412 тестов без ошибок/пропусков, исходники не
изменялись во время прогона. 2082 собранных теста вне объявленного профиля
не выполнялись и не засчитываются пройденными. Ещё три отдельных теста
проверяют контракт восстановления отрицательного случая; они не прибавлены
к числу 1412. Исходный архив полного прогона и его SHA-256 сохранены отдельно
от последующей поправки приёмочного benchmark и заметки статуса.

Первый полный прогон отклонён из-за отсутствия ANDES; повторный выполнен с
hash-pinned ANDES 2.0.0 и motulator 0.19.0 из временных каталогов. Системные
зависимости не заменялись. Исправление проверки восстановления относится
только к benchmark: ранее он ошибочно требовал точного совпадения wall time
у повторно рассчитываемого отрицательного случая. Все численные/сетевые
проверки уже были успешны и не пересчитывались при исправлении этого gate.
Изначальный отрицательный итог сохранён в `original-summary.json`.

Повторить исправленную проверку целостного завершённого корпуса можно без
новых физических расчётов:

```sh
python -m benchmarks.noisy_identification_acceptance \
  --reassess reports/noisy-identification-final-2026-11-08 \
  --out /tmp/reassessed-noise-acceptance
```

Новый полный численный прогон по-прежнему запускается с `--wheel`. Поставка,
wheel, исходники, JUnit, сравнения и SHA-256:
`reports/noisy-identification-delivery-2026-11-08/delivery.json` и `manifest.json`.
Wheel проверен вне репозитория на принятом и отклонённом случаях; отдельный
venv использует уже доступные системные зависимости. Чистая ОС и внешняя
квалификация этим не заявляются. GitHub/CI не используются.
