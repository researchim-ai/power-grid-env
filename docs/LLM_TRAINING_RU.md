# Данные и физический verifier для SFT / GRPO

## Целевая VLM: Qwen3.5-4B

Выбрана `Qwen/Qwen3.5-4B`. Полный локальный checkpoint найден в
`/home/user/workspace/cad-env/artifacts/models/qwen35-4b`; это BF16 safetensors,
а не Ollama/GGUF. Два шарда занимают 9.32 GB. Проверены полные SHA256 против
локального model-origin, индекс всех 738 тензоров и границы данных в заголовках.
Конфигурация содержит `Qwen3_5ForConditionalGeneration` и vision backbone.
Идентификатор ревизии взят из локального происхождения, удалённая аутентификация
источника этой проверкой не выполнялась. Машинная запись:
`requirements/qwen35-local-target.json`.

В существующем окружении `cad-env/.venv-qwen35` с Transformers 5.22.1 успешно
загрузились AutoConfig/AutoProcessor. Тестовое изображение прошло через chat
template: получены 80 image tokens, pixel_values, image_grid_thw и мультимодальная
маска. Замена схемы белым изображением меняет pixel_values. Это подтверждение
обработки изображения процессором, а не использования картинки моделью:
forward весов и optimizer здесь не запускались. CUDA в текущей сессии недоступна.
Результат: `reports/qwen35-local-preflight-2026-11-08/inspection.json`.

Текстовые рецепты ниже **пока не совместимы с этой VLM**: они используют
AutoModelForCausalLM/AutoTokenizer и проверенный стек Transformers 4.57 / TRL 0.27.
Нельзя просто заменить путь на Qwen и считать multimodal SFT/GRPO готовым.
Следующий профиль должен включать:

1. Conditional-generation loader, AutoProcessor и отдельное совместимое
   окружение; сохранение processor вместе с адаптерами/весами.
2. Изображения однолинейной схемы и графиков, построенные исключительно из
   публичной модели и разрешённых наблюдений. Все изображения/аугментации одного
   физического случая должны оставаться в одном topology split.
3. Полный учёт image tokens, image_grid_thw, pixel_values и completion-only
   labels без обрезания изображения или ответа; явный режим enable_thinking.
4. GPU memory/gradient preflight, затем ограниченный LoRA/QLoRA SFT и GRPO
   с физическим verifier. Выбор quantization/vision LoRA — после измерений.
5. Сравнение исходной модели, SFT и GRPO на одинаковом holdout и бюджетах;
   matched / blank / wrong image / text-only контроли, чтобы проверить пользу
   зрения и отсутствие утечки ответа через рендер.

Этот список фиксирует требования следующей реализации; мультимодальное обучение
Qwen и его инженерное качество ещё не квалифицированы. Веса и окружение другого
проекта не меняются и не копируются в git данного проекта.

Это рабочий локальный путь от процедурной схемы к SFT, GRPO и проверке
checkpoint на отложенных топологиях. Первый профиль — восстановление питания
после известного трёхфазного повреждения. Он использует существующий
несимметричный квазистационарный решатель OpenDSS. Динамические двигатели,
EMT и преобразователи проекта пока не превращены в LLM-задачи этим генератором.

## Что реализовано

- Генератор деревьев с резервным вводом: изменяются схема, импедансы,
  несимметричные нагрузки, сопротивление повреждения и идентификаторы.
  Три режима: доступный резерв, недостаточный токовый предел и заблокированный
  резерв. Последние два учат безопасно признавать невозможность полного питания.
- SFT: полный план, отдельные решения после фактических наблюдений и
  многошаговые JSON tool-вызовы `act`/`finish`. Нет выдуманных объяснений,
  chain-of-thought или результатов инструмента. Учитель — лучший допустимый
  из heuristic/aggressive/hold, а не доказанный глобальный оптимум.
- GRPO: 2–32 кандидата для одного состояния; каждый физически выполняется
  с одинакового reset/seed. Есть диагностические преимущества и callback TRL,
  возвращающий **сырые награды**, чтобы нормализация не выполнялась дважды.
- Интерактивный `rollout_tools(task, generate)` с `observe`, `simulate_plan`,
  `act`, `finish`; callback видит только публичную переписку. Прямой
  `GRPOTrainer` в этой версии обучает целый план. Многошаговый tool-policy
  optimizer отдельно не реализован; runner и SFT-траектории доступны.
- Локальные SFTTrainer/GRPOTrainer, сохранение checkpoint, версии библиотек,
  хеши входных/выходных весов и tokenizer, журнал обучения. Затем локальная
  greedy-генерация и физическая оценка **всего** dev/test, без выбора удачных задач.

## Профиль и награда

Горизонт 80 s, действие раз в 10 s, мгновенные переключения, постоянные PQ-нагрузки,
один источник, полные свежие измерения, радиальная работа. Нет скрытых будущих
событий, автоматики, DER или тепловой динамики. Поэтому раннее устойчивое
восстановление можно завершить по действующему критерию Engine; оставшаяся часть
постоянного спроса считается обслуженной. Незавершённый план дополняется hold до
горизонта: короткий ответ не сокращает ENS.

Для допустимого решения:

`reward = clip(0.75 × served_energy_fraction + 0.25 × restored − 0.001 × operations, 0, 1)`.

ENS пересчитывается по физическому журналу. Напряжения под питанием вне допуска,
перегрузки, нарушение блокировок и отвергнутые команды дают −1. Отключение нагрузки
при изоляции повреждения учитывается через ENS, а не запрещается как действие.
Неверный JSON, неизвестное оборудование, лишние поля и самооценка `reward` дают −1.
Сбой/незавершённость решателя дают `reward=null`: группа отбрасывается, TRL callback
останавливает batch, а не учит на ложной отрицательной оценке. Одинаковые награды
дают нулевые преимущества; это не свидетельство обучения.

`simulate_plan` использует только публичную модель и явно сообщает предположения.
Это расчёт конечной схемы, не точный прогноз скрытого повреждения и не проверка
всех промежуточных переключений. Фактическая награда всегда приходит из настоящего
эпизода. Лимиты: 8 физических шагов, 24 tool-вызова, 2 what-if, 32 KiB ответа.

## Данные и разделение

В корпусе `public/{train,dev,test}/{prompts,plans,steps,tools}.jsonl` содержит только
разрешённые входы и наблюдения. `private/tasks` и `private/episodes` — входы и
журналы verifier; их нельзя добавлять к датасету модели. `llm-data export` копирует
только один публичный split/kind. Даже физически открытая задача не раскрывает
в prompt скрытый canary, точный fault_R или привилегированные векторы решателя.

Группы топологий вычисляются по каноническому дереву с отмеченным резервным
подключением. Переименование узлов, перестановка симметричных ветвей и изменение
параметров не создают независимый split. Внутри корпуса такие дубликаты запрещены.
При нескольких shards нужно сохранять **одно и то же назначение семейств split**:
между произвольными отдельно созданными корпусами глобального реестра нет.
Четыре встроенных семейства — небольшой приёмочный набор, не доказательство
обобщения на все реальные сети. Пользовательские `families` задаются списком
`{id, split, parents}`; первый parent −1, следующие меньше индекса ребёнка.
В каждом плане должны быть все три split. Изоморфные семейства отвергаются.

Один корпус ограничен 256 задачами, 1536 суммарными узлами деревьев и байтовыми
бюджетами артефактов. Для больших объёмов генерируйте независимые bounded shards
с фиксированным распределением топологий. Увеличение числа вариантов не увеличивает
число независимых топологий.

Manifest проверяет целостность, не авторство. Семантическая проверка повторяет
генерацию, выбор учителя, физический план, приватный журнал и публичные ответы.
Переписанные и заново запечатанные наблюдения тоже отвергаются. Корпус привязан
к хешу Python-производителя; после изменения кода нужна новая генерация/приёмка.
API — граница данных для текстовых действий, не OS sandbox для недоверенного
Python-кода. Verifier и приватный корпус держит доверенный training host.

## Запуск

Из корня проекта после установки основного пакета:

```bash
power-grid llm-data generate --input cases/llm-training/generation.json --out reports/llm-corpus
power-grid llm-data verify reports/llm-corpus
power-grid llm-data export reports/llm-corpus --split train --kind plans --out reports/sft-public
power-grid llm-data export reports/llm-corpus --split train --kind prompts --out reports/grpo-public
```

Каталоги результата должны быть новыми. По умолчанию получаются 12 задач:
6 train, 3 dev, 3 test. Для GRPO модель получает `prompt` и opaque `task_id`;
приватный сценарий не передаётся в колонки Dataset. Callback:

```python
from power_grid_env.llm_training import CorpusVerifier
verifier = CorpusVerifier("reports/llm-corpus")  # только train по умолчанию
reward_function = verifier.trl_reward
```

Для CLI-проверки группы JSON-файл содержит только `task_id` и `completions`
(список JSON-строк планов):

```bash
power-grid llm-data score-group reports/llm-corpus --input /path/group.json --out reports/grpo-group
```

Оценка готовых предсказаний принимает JSONL `{task_id, completion}` с **каждой**
задачей выбранного dev/test ровно один раз:

```bash
power-grid llm-data evaluate reports/llm-corpus --input /path/predictions.jsonl --split test --out reports/llm-test
```

## Обучение своего checkpoint

Torch/Transformers/TRL — optional extra `.[llm-training]`; основной решатель их
не импортирует. Проверенные прямые версии записаны в
`requirements/llm-training-tested.txt` (это не полный транзитивный/CUDA lock).
Используйте отдельное совместимое окружение. Реальный model checkpoint нужно
подготовить локально: загрузки из сети, remote code и внешние трекеры отключены.
В примерах замените абсолютные пути и выберите доступный CPU/GPU:

```bash
python -m power_grid_env.llm_fit --input cases/llm-training/sft-local.json
python -m power_grid_env.llm_fit --input cases/llm-training/grpo-local.json
python -m power_grid_env.llm_inference --input cases/llm-training/evaluate-local.json
```

Checkpoint должен иметь chat template. Рецепт SFT обучает только completion,
packing выключен. Публичные примеры заранее токенизируются для проверки длины:
схема и ответ не обрезаются молча. GRPO использует стандартный on-policy sampler
TRL, `beta=0`, без vLLM, один локальный процесс в проверенном профиле. Нельзя
выдавать диагностические преимущества `score_group` за готовые reward labels.
SFT для `steps`/`tools` выбирается полем `sft_kind`; direct GRPO принимает `plans`.

Форматы TRL: [SFTTrainer](https://huggingface.co/docs/trl/sft_trainer),
[GRPOTrainer](https://huggingface.co/docs/trl/grpo_trainer). Исполняемый адаптер
проверяется на версиях из файла требований; новая версия требует повторной проверки.

## Проверка и следующая очередь

```bash
python -m pytest tests/test_llm_training.py
PYTHONPATH=. python benchmarks/llm_data_acceptance.py --out reports/llm-acceptance
PYTHONPATH=. python benchmarks/llm_cpu_smoke.py --corpus reports/llm-corpus --out reports/llm-cpu-smoke
```

Последняя команда требует optional training-окружение. Создаётся крошечный GPT2
со whole-message vocabulary и настоящими optimizer/reward вызовами. Это технический
bandit smoke, не языковая/инженерная модель. Его метрики и результаты на test
нельзя трактовать как качество LLM. Учитель и verifier используют один Engine;
эта приёмка не является независимым физическим эталоном. Независимые численные
проверки основного моделера остаются отдельными проверками обязательного профиля.

многошаговый GRPO optimizer; больший публичный topology holdout; реальный
