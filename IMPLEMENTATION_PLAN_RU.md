# Power Grid Environment: план продукта и реализации

Версия 0.3 · 25 октября 2026 · техническая программа реализации агентом.

Цель — реализовать открытую платформу инженерной проверки алгоритмов управления электрическими сетями с доказанной численной достоверностью и средами обучения RL/ML/LLM/VLM. Разработка выполняется пользователем совместно с агентом. План не содержит бюджета, найма и обязательных коммерческих этапов. Порядок работ определяется зависимостями и прохождением проверок, а не календарём.

В репозитории пока нет реализации. Этот документ задаёт архитектуру; основной исполняемый документ — [AGENT_IMPLEMENTATION_SPEC_RU.md](AGENT_IMPLEMENTATION_SPEC_RU.md). При расхождении требований приоритет имеет ТЗ.

## 1. Главная ценность

Проверяемое моделирование нормальных, аварийных и переходных режимов, воспроизводимые сценарии, объяснимые ограничения и обучение агентов на одной согласованной модели. Высокий уровень означает доказанные свойства каждого расчётного режима, а не количество кнопок.

Первый законченный продукт — испытания внешнего алгоритма восстановления распределительного фидера после аварии с трёхфазной несимметрией, явными коммутационными событиями и ограничениями. Полный workflow: импорт модели → preflight → подключение контроллера → suite → сравнение с baseline → отчёт и replay. Пользователь получает нарушения с привязкой к оборудованию и времени, показатели восстановления и комплект воспроизводимых доказательств.

Первый релиз использует проверенный внешний phase-domain solver. Собственный solver нужен только для доказанного пробела; численные требования при этом неизменны. RMS, EMT, магистральные сети и детальные защиты расширяют применимость отдельными модулями и не блокируют выпуск полезного инструмента испытаний. Следующий task pack — проверка DER-управления.

## 2. Что использовать из существующей экосистемы

Физические решатели и исследовательские среды уже существуют. Собственная ценность — согласованная семантика данных, реалистичные среды, мультимодальные наблюдения, проверка действий, управление экспериментами и доказательства качества.

- [pandapower](https://www.pandapower.org/about/) — расчёты режимов, OPF, оценка состояния и короткие замыкания. Использовать для эталонных небольших кейсов и части адаптеров, не считать единственным источником истины.
- [DSS-Extensions / OpenDSSDirect.py](https://dss-extensions.org/OpenDSSDirect.py/) — кандидат на первый backend распределительных сетей. Это отдельная реализация экосистемы OpenDSS; совместимость и версии моделей проверять явно. Существующий расчётный движок не является готовой средой обучения.
- [Grid2Op](https://github.com/Grid2op/) — уже развитая экосистема сред управления сетью, baseline-агентов и генерации временных рядов. Для магистральной вертикали делать совместимость и расширения, а не конкурировать повторением API.
- [LightSim2Grid](https://lightsim2grid.readthedocs.io/en/latest/) — быстрый C++ backend, прежде всего полезный для Grid2Op. Реальную скорость измерять на выбранных сценариях.
- [PowSyBl](https://www.powsybl.org/pages/overview/features.html) — полезен для промышленной модели сети, обменных форматов, анализа надёжности и схем. Поддержка конкретного импортёра зависит от версии и подключённых модулей.
- [ANDES](https://docs.andes.app/en/v1.10.0_a/tutorials/04-time-domain.html) — кандидат для электромеханических переходных процессов. Наличие такого адаптера не означает поддержку EMT.
- [HELICS](https://docs.helics.org/en/latest/) — ко-симуляция инструментов с согласованием времени; включать после появления конкретного междоменного сценария.
- [PyPSA](https://pypsa.org/) — отдельная линия для планирования и оптимизации энергосистем. Не перегружать ею первую операционную среду.

Это проверенные возможности проектов, но выбор комбинации — наша инженерная рекомендация. До зависимости от любого backend: проверить лицензию, численную устойчивость, представление топологии, управление состоянием, многопроцессность и возможность воспроизведения.

## 3. Границы физики

Начать с электроэнергетики: распределение, затем передача. Тепло, газ, водород и межсекторные рынки — расширение через ко-симуляцию после продуктового подтверждения.

Разделить уровни точности:

1. Квазистационарные режимы: последовательность расчётов AC power flow, профили нагрузки, переключения и дискретные регуляторы. Первый продукт — несимметричные трёхфазные сети распределения.
2. Эксплуатационная оптимизация: ограничения напряжения и тока, redispatch, ограничение генерации, накопители, контроль резервов; OPF и MPC как baseline и источник демонстраций.
3. Электромеханическая динамика: частота, регуляторы, возбуждение, устойчивость и отключения. Отдельные модели и договор точности, отдельная валидация.
4. EMT: электромагнитные переходные процессы и подробная силовая электроника. Интеграция специализированного решателя с отдельными эталонами и критериями приёмки.

DC power flow допустим как ускоренный приближённый расчёт для подходящих задач передачи. Он не подтверждает допустимость напряжений и реактивной мощности. Успех квазистационарного эпизода не доказывает динамическую устойчивость. Для каждой среды публиковать паспорт: уравнения, временной шаг, допущения, модели нагрузок, защит и контроллеров, проверенные режимы и известные ограничения.

## 4. Архитектура

Поток исполнения: Scenario → Scheduler → Observation → Agent → Action validator → Event executor → Backend → Constraint evaluator → Recorder. UI и обучение используют один API, а не отдельные копии логики.

Контур испытаний: Import/preflight → Suite runner → изолированный Controller adapter + Simulation → независимый Evaluator → Compare/report/evidence bundle → Replay. Контроллеры могут быть детерминированными, оптимизационными или обученными; наличие AI не требуется для проверки алгоритма. Отказ контроллера, отказ расчёта и физическое нарушение имеют разные статусы. Допущения импорта и границы физики входят в итоговый отчёт.

### 4.1. Каноническая модель

Версионируемые сущности: подстанция, уровень напряжения, terminal, connectivity node, bus, фаза, линия, трансформатор, шина, коммутационный аппарат, нагрузка, генератор, инвертор, накопитель, измеритель и контроллер. Для первого адаптера поддерживать только явно описанное подмножество.

Разделить паспортные данные оборудования, оперативную топологию, физическое состояние, измерения и прогнозы. Состояние выключателя не равно наличию напряжения, а расчётная шина не равна физическому узлу. Для импорта хранить исходные идентификаторы и таблицу соответствия.

Единицы и знаки обязательны: kV, MW, MVAr, A, Hz, MWh; фазные и линейные величины не смешивать; per-unit base указывается явно. Хранить нормальные и аварийные пределы с длительностью, фазность, параметры заземления и достоверность данных. Не заполнять неизвестные параметры молча.

Модель поддерживает quality flags, provenance, версии схемы и миграции. Импорт выдаёт отчёт потерь: какие элементы и свойства не перенесены, какие аппроксимации применены. Неподдерживаемый элемент блокирует задачу или требует явно выбранной аппроксимации.

### 4.2. Backend interface

Минимальный контракт: capabilities(), load_model(), initialize(), apply_events(), solve(), read_state(), snapshot(), restore(), close(). Указывать поддерживаемые физические режимы и элементы. Если native snapshot отсутствует, восстановление выполняется через повторную инициализацию и replay с проверкой результата.

Результат solve содержит convergence, residuals, iteration count, violation details, warnings, island map и классифицированную ошибку. Не выдавать старое состояние за новый успешный расчёт. Различать численную несходимость, некорректные исходные данные, недопустимое действие и физическую потерю питания; несходимость сама по себе не доказательство коллапса.

Отдельный процесс на экземпляр backend, пока не доказана безопасная параллельность контекстов. Привязка канонических ID к solver indices живёт в адаптере. При потере семантики между backend сравнение блокируется с объяснением.

### 4.3. Время и события

Разделить simulated time, wall time и время принятия решения агентом. Очередь событий задаёт причинный порядок: команда, задержка исполнения, изменение оборудования, расчёт, реакция контроллеров/защит, новый расчёт, публикация измерений. Совпадающие timestamps имеют документированный порядок.

Таймеры перегрузки, гистерезис регуляторов, cooldown, отказ аппарата, время переключений и ограничения бригад должны иметь состояние. Для квазистационарной защиты явно описать упрощённый алгоритм; не заявлять релейную достоверность без динамической модели и проверки.

### 4.4. Scenario engine

Сценарий описывает топологию, профили, погоду, генерацию, прогнозы и их ошибки, аварии, ремонт, доступность связи и устройств. Зависимости сохраняются: солнечная генерация связана с погодой, соседние нагрузки коррелированы, массовый отказ не генерируется как независимые монетки.

Процедурные сети проходят инженерные проверки. География не заменяет электрические параметры. Реальные обезличенные модели и синтетические примеры помечаются отдельно. Каждый эпизод имеет seed, scenario hash, model hash, версии библиотек, настройки решателя и журнал событий.

### 4.5. Хранение и инфраструктура

Начало: Python SDK и CLI, JSON/YAML для деклараций, Parquet для траекторий, локальное файловое хранилище, SQLite для индекса. Публичные контракты — JSON Schema и типизированные Python-модели. Числовой hot path использует массивы, а не сериализацию на каждом шаге.

Пилот: FastAPI, PostgreSQL, объектное хранилище с S3 API, очередь заданий и worker-процессы. Изоляция клиента на уровне прав и хранения, лимиты ресурсов, отмена заданий, retry только идемпотентных операций. Распределённые rollout workers и Kubernetes добавляются по измеренной потребности. Не начинать с микросервисов.

Ускорение: профилирование → headless rollout → пакетная запись → переиспользование матриц и warm start при корректности → процессы → векторизация → специализированный C++ hot path. GPU и дифференцируемый решатель — отдельный эксперимент с доказанным выигрышем. Производительность считать в полных environment steps, включая наблюдения и проверки; рендеринг учитывать отдельным режимом.

## 5. Среды для разных агентов

### RL

Gymnasium-совместимый интерфейс reset/step; различать termination и truncation. Наблюдение — dict из числовых массивов, графа, истории, масок и разрешённых прогнозов. Действия — параметризованные переключения, уставки и режимы устройств; непрерывные и дискретные действия должны иметь явные пределы и единицы.

Начать с небольшого пространства допустимых переключений, затем добавить параметризованные/иерархические действия. Action mask не должен вычисляться из скрытой истины, недоступной агенту. При частичной наблюдаемости журналировать, какие сведения использовались для маски.

PettingZoo или аналогичный multi-agent контракт добавить при задаче координации зон/DER. Общая награда, локальные наблюдения, задержки связи и распределение ответственности задаются сценарием.

Baseline: бездействие, существующая автоматика, инженерная эвристика, MILP/MPC при подходящей постановке, RL. Oracle с полной информацией — только отдельно обозначенная верхняя оценка, не честный соперник частично наблюдающего агента.

### LLM

Инструменты с типизированными аргументами: get_observation, inspect_equipment, query_allowed_history, read_procedure, simulate_plan, submit_plan. Доступ к truth state и будущим авариям исключён. Ветка simulate_plan копирует только разрешённую модель/оценку состояния и публикует допущения.

Длинное действие представляется планом с предусловиями, ожидаемыми эффектами, сроками и точками повторной проверки. Валидатор проверяет оборудование, топологию, блокировки, порядок, допустимость полномочий и ограничения. Ошибки инструмента — структурированные; агент может восстановиться после них.

Обучение: демонстрации инженеров и baseline-решателей → imitation/SFT → проверка на скрытых задачах → при необходимости RL по проверяемому результату. Не требовать скрытые цепочки рассуждений: хранить команды, краткое обоснование, использованные источники и измеримые последствия.

Измерять task success, небезопасные попытки, число tool calls, latency, стоимость эпизода и качество отказа от действия при недостатке данных. Сбои API модели и ограничение токенов — часть протокола оценки.

### VLM

Рендерер строит однолинейную схему, таблицу телеметрии, тревоги и тренды из той же опубликованной observation, что доступна агенту. Ground truth и будущие события не просачиваются через цвета, подписи, скрытые DOM-атрибуты или имена файлов.

Два отдельных трека: изображение + структурированные инструменты; только изображение + клики/ввод. Для второго нужен управляемый UI-сервер с hit testing, фокусом, подтверждением команд и задержками, а не статичная картинка. Идентификаторы и аннотации объектов используются для supervision, но не передаются агенту в режиме pixels-only.

Задачи: найти отключённую секцию, сопоставить тревогу с элементом, прочитать состояние аппарата, составить и исполнить переключения. Варьировать раскладку, масштаб, обозначения, язык, темы, шум и задержки обновления. Отложенные стили и раскладки обязательны для теста; иначе модель запомнит интерфейс.

3D-подстанции и физические обходы — отдельная поздняя вертикаль. Для первой ценности достаточно хороших 2D-схем.

### ML

Генерация датасетов для прогнозирования нагрузки/генерации, оценки состояния, обнаружения аномалий, предсказания нарушений и GNN-surrogate моделей. Каждый sample несёт topology hash, timestamp, feature provenance и допустимый horizon. Нормализация обучается только на train.

Surrogate ускоряет screening и предлагает действия; финальная проверка идёт через физический backend. За пределами обучающего распределения использовать fallback. Дифференцируемый power flow не объявлять обязательным требованием MVP.

## 6. Вознаграждение и проверяемая оценка

Не сводить качество к одному reward. Сначала учитывать жёсткие нарушения, затем качество обслуживания, затем экономику и число операций. Конфликтующие критерии показывать раздельно.

Основные метрики: недоотпуск энергии (MWh), время восстановления (мин), доля обслуженной критической нагрузки, величина и длительность нарушений напряжения/тока, нарушения блокировок, число переключений, стоимость управления и wall-clock задержка. Для динамических задач добавить frequency nadir, RoCoF и settling time с определёнными окнами измерения.

В награде штрафы могут зависеть от тяжести и времени нарушения; hard constraints должны проверяться независимо. Сохранять предложенное, отклонённое и фактически исполненное действие. Если safety shield исправляет команду, отдельно показывать качество исходной политики и системы policy+shield.

Разбиение данных: по семействам топологий, временным периодам, погодным режимам, типам отказов и UI-стилям. Нельзя считать новые seeds той же сети проверкой переноса на новую сеть. Отдельные тесты: in-distribution, unseen topology, ошибки модели, частичные измерения, задержки и редкие тяжёлые события.

Фиксировать бюджет агента: информация, доступные действия, число what-if расчётов, время и вычисления. Публиковать распределения результатов по seeds и доверительные интервалы, а также хвостовые риски. Размер тестовой выборки выбирать по требуемой точности и частоте редких событий; 100 успешных эпизодов не доказывают промышленную безопасность.

Закрытый holdout обслуживается отдельным evaluation runner. Разработчик не получает скрытые параметры до завершения оценки. Обновления benchmark версионируются; для управляемого LLM фиксировать провайдера, идентификатор модели, дату, sampling и доступные инструменты.

## 7. Что означает промышленное качество

### Физическая валидация

- Проверки уравнений баланса, единиц, знаков, потерь и пределов, включая острова, обесточенные узлы и реактивные ограничения.
- Эталонные кейсы с аналитическим ответом; сопоставление с независимым решателем только при одинаковых моделях оборудования, регулирования и slack.
- Негативные случаи: неверная фазность, пропущенные данные, недопустимая топология, отсутствие источника, плохая обусловленность, отказ решателя.
- Сложные элементы: РПН, фазосдвиг, ZIP-нагрузка, ограничения инверторов, накопитель с эффективностью/SoC, распределение мощности между источниками. Включать по мере необходимости и валидировать отдельно.
- Для каждого семейства кейсов заранее задать допуски residual, напряжений, потоков и событий. Универсальный процент совпадения непригоден около нулевых величин и границ режимов.
- Два решателя, разделяющие код или ошибочную модель, не дают независимого доказательства. Требуются аналитические проверки и инженерная экспертиза.

### Качество ПО

Типизация, контрактные тесты адаптеров, numerical regression, property-based проверки, fuzzing импортёров, тесты миграций, детерминированный replay и CI на поддерживаемых ОС. Зафиксированные зависимости, SBOM, подписанные релизы, политика уязвимостей и поддерживаемые версии.

Воспроизводимость определить уровнями: полное совпадение в зафиксированном окружении; численная эквивалентность в допусках между платформами; отсутствие гарантии повторения недетерминированного внешнего LLM. Snapshot хранит RNG, таймеры, контроллеры, очереди событий и историю наблюдений, а не только напряжения.

### Эксплуатация

Ограничения памяти/времени заданий, метрики solve latency и rollout throughput, классифицированные ошибки, traces, отмена, checkpoint/resume. У коммерческого пилота — процедура backup/restore с проверкой восстановления, аудит действий, разграничение ролей и изоляция данных заказчиков. SLO согласовываются с пилотом после измерений.

Контрольные ступени применения: лабораторная симуляция → offline replay реальных событий → shadow mode без управления → инженерная рекомендация → ограниченная автоматизация после отдельной инженерной приёмки. Наличие симулятора и benchmark не является разрешением управлять реальной сетью.

## 8. Открытый и коммерческий продукт

Открыто: каноническая схема, Python SDK/CLI, один полноценный backend, локальные среды RL/LLM/VLM, базовый UI, сценарии, baseline-агенты, evaluation protocol и локальный recorder. Путь от установки до первого эпизода должен быть бесплатным и воспроизводимым.

Платно: управляемые вычисления, частные каталоги сценариев и моделей, совместные проекты, SSO/RBAC, аудит, интеграции с данными клиента, развёртывание on-prem/VPC, поддержка и SLA, инженерная валидация конкретного применения.

Предпочтение для собственного ядра — permissive open source, например Apache-2.0, после проверки совместимости зависимостей. Вести реестр лицензий кода, моделей, данных и примеров; коммерческие права на данные не следуют автоматически из лицензии программы. Проверить лицензии каждой закреплённой версии и условия распространения бинарных сборок. Это задача перед релизом с юридической проверкой, не готовое правовое заключение.

Не делать закрытый формат модели, без которого открытая версия бесполезна. Защита бизнеса: доверие к валидации, качество интеграций, сценарии с правомерно полученными данными, удобство рабочего процесса и платящая сеть партнёров. Один новый solver или лидерборд легко не превращаются в устойчивый бизнес.

Управление проектом: CONTRIBUTING, CODE_OF_CONDUCT, security policy, RFC/ADR, публичная roadmap, DCO либо продуманная CLA, понятные права сопровождающих. Внешние backend и сценарии имеют собственные версии и паспорта качества.

## 9. Исполнение агентом

Декомпозиция по физическим подсистемам, обязательные эталоны, численные допуски и порядок реализации определены в [AGENT_IMPLEMENTATION_SPEC_RU.md](AGENT_IMPLEMENTATION_SPEC_RU.md). Агент проходит этапы последовательно, сохраняет артефакты проверки и не помечает функцию готовой по одному успешному demo.

Первая поставка проходит A → B → C → D → P из ТЗ: физические контракты и reference cases; проверенный phase-domain backend; время и replay; restoration и интерфейсы агентов; затем импорт внешней модели, подключение внешнего контроллера, suite runner, независимый evaluator, отчёт и минимальный инженерный просмотр. Расширения E–H следуют отдельно. Большие обучающие запуски и оптимизация скорости начинаются после численной приёмки.
