# Работающий двигатель, защиты и действительное прекращение подпитки КЗ

## Профиль R06.32 / DES-04

Источник через трансформаторный эквивалент и100м горячего кабеля питает
авторский двигатель75kVA/400V и постоянный Z нагрузки. Все паспортные
эквиваленты, исходные настройки VI и условия находятся в `base-original.json`.
Новый профиль проверяет КЗ после3с реального разгона, а не из нулевой ЭДС.
Это отдельный инженерный профиль, не распространение всей предыдущей
квалификации на произвольные машины и режимы.

Предел владельца: источник отключён и полный ток КЗ погашен не позже150мс.
Погасание определяется как RMS≤0.1A **во всех последующих сохранённых
отсчётах активного КЗ**, с наблюдением не менее20мс до внешнего удаления
повреждения. КЗ подаётся в3.0с, планово удаляется в3.3с, расчёт идёт до3.5с.
Предел не заменён моментом планового удаления. Скорость перед КЗ≥0.9pu,
двигатель должен быть подключён; после погасания требуется его отключение.
Максимальный шаг вывода2мс, finer grids1мс и0.5мс. Это **сетки вывода**,
а не самостоятельное доказательство сходимости по шагу интегратора.

Три аварии: основная защита; отказ её выключателя с резервным отключением;
потеря измерения основной защиты с независимым резервом. В каждой паре
единственное различие — наличие контактора с контролем напряжения двигателя:
порог отключения0.3pu, возврата0.8pu, выдержка отключения90мс,
автоматические повторные пуски запрещены. Не вводится запланированная команда
отключения двигателя, которая заранее знала бы момент КЗ.

Подтверждается физическое состояние аппаратов, ток линии/состояние источника,
пары pre/post события открытия, задержки от запроса, ожидаемые реле,
отсутствие лишних действий и независимо восстановленные часы реле.
Статор алгебраический: после физического отключения мотора его ток обнуляется,
но внутренняя ЭДС и механическое состояние искусственно не сбрасываются.

## Исходная и отдельная новая уставка

VI backup TMS0.07 была проверена в прежнем профиле с другими временными
условиями. Она не выполняет **новый** предел150мс при потере основного CT:
в шести контрольных прогонах к удалению КЗ progress достигает лишь≈0.7303135.
Это отрицательное инженерное свидетельство при исправных часах и физике,
а не ошибка решателя. Даже установленный UV-контактор этого отказа не исправляет:
он удаляет моторную подпитку, но источник всё ещё питает КЗ.

`base-revised.json` отличается от исходного **только label и backup TMS0.015**.
Pickup, остальные защиты, допуски, оборудование и исходные критерии не меняются.
Квалификация ревизии относится к её номинальным уставкам; все16 tolerance
corners предыдущего этапа для новой TMS пока не выполнены.

## Воспроизведение

Из корня, каждый OUT должен отсутствовать:

```bash
python -m benchmarks.running_fault_protection_reference \
  --base cases/running-fault-protection/base-revised.json --out OUT_FAULTS
python -m benchmarks.running_fault_revision \
  --original cases/running-fault-protection/base-original.json \
  --candidate cases/running-fault-protection/base-revised.json --out OUT_REVISION
python -m benchmarks.running_fault_normal_modes \
  --base cases/running-fault-protection/base-revised.json --out OUT_NORMALS
python -m benchmarks.motor_fault_branch_duty --source OUT_FAULTS --out OUT_DUTY
python -m benchmarks.running_fault_acceptance \
  --faults OUT_FAULTS --revision OUT_REVISION --normals OUT_NORMALS \
  --duty OUT_DUTY --out OUT_ACCEPTANCE
```

`power_grid_env.running_fault_protection` также запускает отдельный study:
`python -m power_grid_env.running_fault_protection --study STUDY.json
--requirements REQUIREMENTS.json --out OUT`. Требования всех отсчётов и
study-json хранятся в каждом дочернем каталоге корпуса. Выход2 означает
непройденный профиль; отрицательный результат сохраняется.
`verify_clearance(..., expected_study=..., expected_requirements=...)`
требует оба owner-inputs, сверяет trace identity и пересчитывает оценку.
Это оценка переданной траектории, а не повторная интеграция физики.

Положительные пакеты:
`reports/running-fault-protection-qualified-2026-11-13`,
`reports/running-fault-revision-2026-11-13`,
`reports/running-fault-normal-modes-2026-11-13`,
`reports/running-fault-branch-duty-2026-11-13`,
`reports/running-fault-acceptance-final-2026-11-13`.
Исходная ревизия в aggregate числится только отрицательным контролем.

## Открытые границы

Горячий двухузловой профиль при номинальном питании, один single-cage мотор,
авторские нагрузка/инерция и параметры защит. Нет гарантии непрерывного
погасания между отсчётами, физики дуги/статора/DC/пиков, неизвестных OEM
выдержек и общей селективности. Нельзя автоматически наследовать cold/hot
монотонность пассивной сети для машины с меняющейся ЭДС. Остаются tolerance
corners новой ревизии, другие моторы/топологии, несимметричные КЗ,
температурная обратная связь, полный интеграционный независимый эталон.
Награды для обучения и нормативного одобрения этот профиль не выдаёт.

Локальная поставка: `reports/running-fault-delivery-2026-11-13` с wheel,
исходниками протокола, XML264 тестов и6 повторно интегрированными случаями
из установленного wheel вне исходников (3 positive/3 negative). Arrays,
события, настройки и оценки совпали; runtime wall-time metadata не обязано
совпадать. Python `-I`, reference imports заблокированы. Это тот же host,
общие библиотеки и import guard, а не OS sandbox. Основные60 траекторий
привязаны manifest-хешами в sibling-папках,6 installed-native пакетов включены.
