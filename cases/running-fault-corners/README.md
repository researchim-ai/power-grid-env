# Допуски защит работающего двигателя: углы, контрпримеры и ревизия

## Итог R06.33, 15 ноября 2026

Квалифицирован **отдельный** вариант VI: primary TMS0.009, backup TMS0.0155.
Номинал и все16 знаковых комбинаций pickup±5%/TMS±10% основной/резервной
защит проверены на работающем двигателе после3с разгона. В каждом варианте:
пуск, повторные провалы, выбег/повторный пуск и три аварии — primary,
breaker failure, потеря измерения primary. Два решателя ×три сетки вывода:
36 исследований на вариант, **612 реально выполненных расчётов**.

При авариях сохранены критерии R06.32: подключённый мотор перед КЗ со
скоростью≥0.9pu; отключение сетевой подпитки и sampled-погасание полного
тока КЗ≤0.1A в150мс; наблюдение≥20мс до внешнего снятия КЗ. UV-контактор
0.3pu/90ms без auto-restart. Нормальные критерии скорости, токов, напряжения,
нагрева и состояния переданы без ослабления. TMS при углах реализуется в
конкретных настройках; остаточные tolerances обнуляются, второй слой не
начисляется. Номинальные паспорта сохраняют исходные tolerances как описание.

Дополнительно прошли **48** случаев на двух выбранных критических углах:
1100 для primary и0011 для measurement-loss при20/90°C и0.95/1.05U,
с обоими решателями и тремя сетками вывода. При низком U и горячем кабеле
самое позднее сетевое отключение≈145.857мс, запас до150мс≈4.143мс.
Это не все16 углов при каждой температуре/напряжении и не непрерывный
доказанный диапазон неопределённости. Трансформаторный R/X фиксирован.

Итого для финальной ревизии: **660 положительных исследований**,330 пар
Radau/DAE для положительных случаев;6 дополнительных парных отрицательных
контролей прежней ревизии (ещё3 пары решателей). По306 аварийным траекториям
полной матрицы рассчитаны по-портовые RMS I²t и102 fine-pair сравнения.
Сетки вывода2/1/0.5мс не объявляются сходимостью по шагу интегратора.

## Что нашли, вместо автоматического переноса nominal approval

1. Прежняя primary0.01/backup0.015 при nominal U на углу1100 почти достигает
   лишнего backup-trip: progress≈0.998934. При1.05U резерв действительно
   срабатывает, хотя primary исправна; оба решателя воспроизводят отказ.
2. Промежуточная primary0.01/backup0.0155 прошла свою горячую nominal-U
   матрицу612, но теряет селективность при20°C/1.05U на углу1100. Шесть
   настоящих физических отказов на всех трёх сетках сохранены.
3. Финальная primary0.009/backup0.0155 сокращает время основной защиты,
   сохраняя приемлемое время резерва. По сравнению с промежуточной меняется
   только primary TMS и имя. По сравнению с вариантом R06.32 меняются две
   TMS и имя. Pickup, физика, выдержки аппаратов, fault schedule и критерии
   не ослаблялись. Ускорение TMS не выдаётся за паспортную настройку OEM.

Всего выполнены1332 исследования исследовательской программы:612 горячих
промежуточных +54 предварительных граничных +612 финальных +54 финальных
граничных. Это не1332 положительных результата финального варианта.

## Исправления эталона и сохранение отрицательных свидетельств

У старого SI oracle обнаружились два ограничения: он предполагал, что
физическая ЭДС источника равна базе напряжения шины; его полная матрица
также вырождалась после отключения обоих питающих портов изолированной шины.
Новый `running_fault_island_reference` использует фактическое `source.ll_v`
и ограничивает решение только для точно нулевых невозбуждённых строк.
Не добавляется фиктивный шунт, ненулевое возбуждение не отбрасывается.
Для обоих случаев добавлены отдельные регрессионные тесты.

Исходные54+54 граничные траектории и ранние отчёты с неуспехом эталона
**не переписаны**. Все108 уже запечатанных native-траекторий повторно
проверены новым oracle без новой интеграции. Положительный итог этой
проверки находится в `reports/running-boundary-reassessed-2026-11-15`.
Он сохраняет шесть настоящих отказов промежуточной схемы, а не объявляет
её подходящей. Старый oracle с совпадающим хешем архивирован в поставке.

## Запуск

Из корня. `protocol.json` — промежуточный0.01/0.0155,
`protocol-revised.json` — финальный0.009/0.0155. Выход должен отсутствовать:

```bash
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 \
python -m benchmarks.running_fault_corner_store \
  --protocol cases/running-fault-corners/protocol-revised.json \
  --out reports/my-running-corners --workers 4

python -m benchmarks.running_fault_corner_store \
  --protocol cases/running-fault-corners/protocol-revised.json \
  --out reports/my-running-corners --verify

python -m benchmarks.running_fault_joint_boundary \
  --previous cases/running-fault-corners/protocol.json \
  --revised cases/running-fault-corners/protocol-revised.json \
  --original cases/running-fault-protection/base-revised.json \
  --out reports/my-running-boundary --workers 4
```

Для восстановления незавершённой матрицы есть явный `--resume`: запечатанные
исследования повторно проверяются и используются без новой интеграции.
Owner-протокол и producer должны совпадать; незапечатанный повреждённый
дочерний пакет не удаляется и не подменяется автоматически. `--workers`1..8.
Solver budget остаётся заданным в runtime_limits; этот benchmark не является
OS sandbox. Унаследованный `ProtectionEnvelope.total_timeout_s` не является
жёстким глобальным таймаутом этого составного исполнителя; при необходимости
задайте отдельный лимит времени внешним supervisor.

## Артефакты и верификация

Составное хранилище содержит `index/` и `studies/`. Индекс запечатан отдельно;
каждый из17 вариантов и каждый из его36 исследований имеет собственный seal.
Общие лимиты `study_artifacts` не увеличивались. `verify_store` с обязательным
owner-протоколом восстанавливает recipes, проверяет покрытие/раскладку,
пересчитывает критерии, часы, независимый условный SI oracle, пары решателей
и I²t; затем повторно проверяет hashes. Чтение требует неизменяемого store;
атомарная защита от параллельного автора не заявляется.

Финальные данные:

- `reports/running-fault-revised-corner-store-2026-11-15` —612 финальных.
- `reports/running-fault-joint-boundary-2026-11-15` —48+6 native; старый
  неуспех oracle оставлен, использовать совместно с reassessment.
- `reports/running-boundary-reassessed-2026-11-15` —скорректированный аудит108.
- `reports/running-corner-accepted-2026-11-15` —общий owner-bound gate.
- `reports/running-fault-corner-store-2026-11-15` и
  `reports/running-fault-boundary-2026-11-15` —промежуточный, более широкий
  профиль не прошедший; не включать в положительное доказательство финальной ревизии.

Проверены277 целевых тестов, включая13 новых: owner/producer mismatch,
искажённое CT даже при неизменных часах, incomplete coverage, cached resume,
границы worker budget, точная ревизия и два дефекта SI oracle. Все прошли
без ошибок/пропусков. Это не полный suite и не повтор недоступных ANDES cases.
Численный runtime не менялся; используется ранее закреплённый wheel.
Никаких наград для обучения или нормативного одобрения профиль не выдаёт.

Следующая очередь: полное декартово произведение сетевых условий и релейных
допусков, внутренние точки/предельные сценарии с измеренным запасом, другие
машины/топологии, температурная обратная связь и независимая динамика.

Локальная поставка `reports/running-corner-delivery-2026-11-15` содержит
закреплённый неизменённый wheel R06.32, протоколы, источники benchmark,
архив диагностического oracle,277-test XML, aggregate acceptance и6 новых
native replays установленного пакета (5 положительных/1 отрицательный).
Работа вне checkout с Python-I и запретом reference imports; физические
массивы/события совпали точно. Тот же host и общие зависимости, не OS sandbox.
Все6 installed packets и входы воспроизведения включены.1332 основные traces
не продублированы в поставке: привязаны manifest-хешами sibling stores.
